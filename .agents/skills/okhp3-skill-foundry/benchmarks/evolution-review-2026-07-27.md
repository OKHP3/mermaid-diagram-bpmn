# Skill Foundry 3.0.0 Evolution Review

## Outcome and boundary

Strengthen the Foundry as a portable, evidence-led method for creating and
improving Agent Skills, then synchronize authorized copies. This review changes
the Foundry package and its mirrors only. It does not claim a fresh live
benchmark, publish a package, or modify unrelated application work.

## Candidate inventory

Twelve scoped `okhp3-skill-foundry` instances were found in the local mirror
collection. The active and distribution copies in `skillz` had identical
resources but divergent `SKILL.md` files. The active copy had the most detailed
execution protocol, the distribution copy had the clearest concise workflow,
and an older 1.1.0 copy contributed a useful standards and trust preflight.

The 3.0.0 baseline is a reviewed synthesis. No candidate was selected because
it was longer, newer by label, or more numerous.

## Current evidence consulted

- [Agent Skills specification](https://agentskills.io/specification): portable
  frontmatter limits, resource layout, progressive disclosure, and validation.
- [OpenAI skill guidance](https://learn.chatgpt.com/docs/build-skills):
  front-loaded descriptions, local discovery, optional `agents/openai.yaml`,
  and skill testing guidance.
- [Anthropic Agent Skills overview](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills): progressive disclosure as a core design principle.
- [GitHub Copilot agent skills](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills): cross-client skill locations and portable package model.
- Directory and marketplace sources supplied for this review: agentskill.sh,
  SkillsMP, AgenticSkills, and skills.sh. These were used as discovery signals,
  not as normative requirements.
- Prompt Equilibrium framework attachments supplied by the package owner:
  treated as a conceptual source for conditional dissent, provenance ledgers,
  semantic-interference controls, and evidence negotiation. Their platform and
  research claims were not adopted as current normative facts without separate
  verification.

The detailed source authority, retrieval dates, review passes, hypotheses, and
applicability limits are preserved in
`benchmarks/learning-ledger-2026-07-27.json`.

## Accepted changes

1. Front-load the job and trigger terms in descriptions rather than branding.
2. Separate portable core instructions from optional host adapters.
3. Replace fixed evaluation counts and universal thresholds with risk-aware
   defaults, explicit acceptance criteria, and development versus holdout sets.
4. Require provenance for every material change and preserve historical
   benchmark status when the evaluated version differs from the current one.
5. Add a recursive renewal and synchronization phase with a canonical-source
   decision, hash verification, semantic review, and a stopping rule.
6. Update the brand, evaluation, grading, template, and adapter references so
   the package teaches the method it now follows.
7. Add an equilibrium-inspired review protocol: materially concordant reviews
   trigger a falsification pass; material disagreement triggers evidence-based
   negotiation or a deferred decision. This is process control, not a claim that
   the package computes a formal Nash equilibrium.

## Rejected or constrained changes

- No new live benchmark was fabricated. Version 1.0.0 live evidence remains
  historical; 3.0.0 evaluation cases are design-ready and await comparable runs.
- No experimental `allowed-tools` restriction was made a portability condition.
- No marketplace score, popularity count, timestamp, or version label was used
  as a standalone quality signal.
- No host-specific automation was made a requirement for the portable skill.
- No consensus result, including independent-agent agreement, is treated as
  proof of perfection or a substitute for version-matched live evidence.

## Release evidence

The final validation results and mirror verification belong in the task handoff.
Any live 3.0.0 benchmark must record runner, model, fixtures, sample count,
evaluated version, and known limitations before it can support a release claim.
