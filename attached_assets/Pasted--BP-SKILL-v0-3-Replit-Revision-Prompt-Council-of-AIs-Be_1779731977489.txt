## WHAT CHANGED IN v0.3

This prompt supersedes v0.2. The delta comes from a three-model Council
evaluation (Claude, ChatGPT Deep Research, Perplexity Deep Research).
Key changes:

SIPOC output contract is now precise and sourced:
5-column table (S–I–P–O–C), completion sequence: Outputs first,
then Customers, then backfill Inputs and Suppliers. Process column
limited to 3–7 high-level steps. No separate SIPOC variable file
needed — derives from organization-profile.md and process-taxonomy.md.

RACI “one A per task” is now a hard validation rule, not guidance:
Enforced by validate-raci.mjs with named diagnostic error code
RACI-V01. RASCI variant (“S – Support”) is supported alongside R/A/C/I.

SOP/WI four-tier hierarchy is now a normative output contract:
Policy/Manual → SOP/Procedure → Work Instruction → Records/Forms.
Each Work Instruction MUST carry parent_sop_id and parent_process_id
fields traceable back to PNS.md step IDs. WI→SOP→PNS traceability
is a validation rule enforced by validate-sop.mjs.

Ecosystem gap characterization is now evidence-based, not assumed:
Existing public skills are point solutions only. Named repos:
markdown-viewer/skills bpmn (PlantUML diagram-only),
ClaudSkills “Bpmn” (PlantUML wrapper),
MCP Market “Process Modeling” (single-skill BA assistant),
45ck/business-analysis-skills (SKILL.md format, not BABOK-conformant).
IBM “Bob skills” is a proprietary BPMN-to-agent precedent.
None constitutes a lifecycle-complete standards-conformant suite.

Five adoption blockers are now documented in the README:
1. Standards licensing — BABOK/CBOK/APQC are paywalled; cite by
section number only, never embed copyrighted content.
2. Tooling focus — agent runtimes optimized for code execution,
not long-running multi-skill discovery engagements.
3. Vocabulary alignment — BABOK, BPM CBOK, and APQC PCF use
incompatible ontologies; the Variable Layer is the bridge.
4. Cross-skill pipeline semantics — no existing open standard
for typed artifact handoff between skills; PNS.md is BP-SKILL’s
answer.
5. Variable layer configuration overhead — must ship minimal
viable defaults to lower onboarding friction.

PNS status lifecycle moved from 9 to 10 states:
Added “scoped” between “draft-intake” and “elicited” to align with
ChatGPT’s normative lifecycle, and added “analyzed” between “modeled”
and “validated” to match the gap-analysis skill’s output state.

## STRATEGIC CONTEXT

BP-SKILL is a domain extension to the Agent Skills open standard
(agentskills.io). It does not alter SKILL.md syntax. It standardises a
15-skill array, a 9-file variable layer, and the Process Narrative
Specification (PNS) handoff artifact on top of the base format.

The operating model is:

```
The playground is for people.
The skills are for agents.
The prompt packs are the universal fallback.
The repos are the source of truth.
The Repls are the manufacturing floor.
```

Skills are the AI analogue of SOPs: permanent, executable, version-
controlled instruction sets that auto-activate on semantic match. The
framing is intentional and should appear in the README and in each
SKILL.md Purpose section.

The three-layer architecture:

```
LAYER 1 — DISCOVERY
BABOK v3-aligned intake, elicitation, stakeholder mapping.
Produces: Process Intake Record (pir.yaml), stakeholder register.

LAYER 2 — NARRATIVE
Process Narrative Specification (PNS.md) — the canonical handoff
artifact. ISO 9001 §4.4.1 process-box structure. BABOK Core Concept
Model anchoring. IEEE/ISO/IEC 29148 information discipline.

LAYER 3 — VISUAL AND DECISION MODELING
bpmn-beta (OKHP3 prototype DSL) as the visual output layer.
DMN 1.4 for externalised decision logic (when ≥ 3 gateway branches
carry policy logic — MUST trigger, not SHOULD).
```

#### SKILL 12 — sop-and-work-instruction-generation

status: core
standards_refs:

- “ISO 9001:2015 §7.5.1–§7.5.3 (Documented information)”
- “BPM CBOK v4.0 KA 4 (Process Design)”
  consumes: PNS.md [validated], organization-profile.md,
  regional-context.md, compliance-controls-registry.md,
  role-dictionary.md
  produces: sop/<process-id>/SOP-<n>.md
  sop/<process-id>/WI-<role>-<step>.md

SOP/WI FOUR-TIER HIERARCHY (normative, sourced from ISO 9001 and
quality management converging convention):
Tier 1: Policy/Manual — “what and why” — NOT produced by this skill
Tier 2: SOP/Procedure — “what happens, who does it, in what sequence”
THIS SKILL produces Tier 2
Tier 3: Work Instruction — “step-by-step how to perform one task”
THIS SKILL produces Tier 3
Tier 4: Records/Forms — evidence artifacts — NOT produced by this skill

SOPs are governance-oriented: overall procedure, responsibilities,
sequence, controls. Subject to formal change control.

Work Instructions are execution-oriented: precise step lists, tools,
parameters, safety notes.

TRACEABILITY RULES (enforced by validate-sop.mjs):

- Every SOP MUST carry: parent_process_id → PNS.md process_id
- Every WI MUST carry:  parent_sop_id → SOP document ID
  parent_process_id → PNS.md process_id
  source_step_ids[] → PNS.md act-NNN step IDs
- WI→SOP→PNS traceability chain is a validation failure if broken

Compliance-controls-registry.md MUST specify which processes require
SOPs, which require WIs, and which are governed by GMP, ISO 9001, or
other frameworks with different documentation requirements.

Never merge SOPs and WIs into a single artifact.

status: core
standards_refs:

- “BABOK v3 Technique §10.39 (Roles and Permissions Matrix)”

  consumes: PNS.md, role-dictionary.md, organization-profile.md
  produces: governance/<process-id>/RACI.md

RACI OUTPUT CONTRACT (sourced from Wikipedia, Cornell, BC Government):
Matrix structure: rows = tasks/activities, columns = roles
Cell values: R (Responsible), A (Accountable), C (Consulted),
I (Informed), S (Support — RASCI variant, optional)

RACI VALIDATION RULES (enforced by validate-raci.mjs):
RACI-V01: EXACTLY ONE A per task row — HARD FAILURE if violated.
Diagnostic: “Task {act_id} has {n} Accountable roles;
exactly one is required.”
RACI-V02: All role IDs in matrix must exist in role-dictionary.md
or be declared provisional
RACI-V03: No task row may be entirely empty
RACI-V04: R count per task should be minimised; warn if > 3

RASCI variant: add S column when process requires explicit “Support”
designation distinct from Responsible.

#### SKILL 14 — sipoc-generation

status: core
standards_refs:

- “BABOK v3 Technique §10.42 (Scope Modelling)”
- “Six Sigma DMAIC Define phase (SIPOC convention)”
- “ISO 9001:2015 §4.4 (process boundary context)”
  consumes: PNS.md [preferred] or pir.yaml [early-stage use]
  produces: governance/<process-id>/SIPOC.md
  governance/<process-id>/SIPOC.yaml

SIPOC OUTPUT CONTRACT (sourced from TechTarget, Six Sigma US, Iowa DoM):
Format: five-column table S–I–P–O–C
Process column: 3–7 high-level steps ONLY — not detailed activity flow
Completion sequence (Six Sigma DMAIC convention):
1. Define Outputs (what the process delivers)
2. Identify Customers (who receives the outputs)
3. Identify Inputs (what is consumed or transformed)
4. Identify Suppliers (who provides the inputs)
5. Map Process steps (3–7 steps connecting inputs to outputs)
SIPOC-R variant: add Requirements column after Customers when
customer requirements are explicitly known

Each row maps to APQC PCF element IDs from process-taxonomy.md.
SIPOC derives entirely from existing variable files — no separate
SIPOC configuration file is needed or created.

Validation: SIPOC must remain consistent with the detailed PNS.md
narrative. If process steps in SIPOC do not align with PNS Main Flow,
flag as SIPOC-V01 warning.

## PNS STATUS LIFECYCLE (10 states — normative)

v0.3 adds “analyzed” as a distinct state between “modeled” and “validated”
to match the gap-analysis skill’s output state precisely.

States MUST progress sequentially. Skills MUST NOT advance PNS.md
beyond their own output state.

```
draft-intake         → set by: process-intake-and-scope
scoped               → set by: stakeholder-and-role-mapping
elicited             → set by: elicitation-and-interview-facilitation
documented-as-is     → set by: as-is-process-capture
modeled              → set by: process-narrative-authoring
analyzed             → set by: process-gap-and-exception-analysis
validated            → set by: process-validation-and-quality-scoring
packaged             → set by: publication-and-handoff-packaging
published            → set by: publication-and-handoff-packaging
                               (after approval gate clears)
deprecated           → set by: any authorized role post-publication
```

  BPMN XML round-trip, or full BPMN 2.0 conformance

    Alignment to Strategy and Goals → Architect Changes →
    Develop Initiatives → Implement Changes →
    Measure Success / Benefits Realisation
  The generic vendor lifecycle (Plan / Analyze / Design /
  Implement / Monitor / Optimize) is non-canonical for CBOK v4.0
  and MUST NOT be used
- APQC PCF element IDs (five-digit) are stable;
  hierarchy IDs are version-dependent — always store both
- Skills are the AI analogue of SOPs: this framing appears in
  README and in each SKILL.md Purpose section
