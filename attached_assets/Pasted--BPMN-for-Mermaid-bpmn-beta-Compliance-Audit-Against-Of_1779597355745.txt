# BPMN for Mermaid (bpmn-beta) — Compliance Audit Against Official Mermaid Directives

## TL;DR
- **The project's overall direction is compatible with Mermaid's official directives, with two material gaps to close**: the parser must move to Langium before any upstream PR (JISON is now explicitly deprecated for new diagrams; the official "Adding a New Diagram" page on mermaid.ai links only to Langium PRs as references), and the aria-roledescription key should be lowered to `bpmnDiagram` to match the documented convention exemplified by `deploymentDiagram`. Everything else — the external-plugin-first strategy, the `-beta` suffix, hand-written D3/SVG rendering, theming via `getStyles(options)`, the no-bpmn-js bundle-size discipline, and accTitle/accDescr via commonDb — is on or near the documented happy path.
- **BPMN is genuinely absent from Mermaid core today** (Mermaid v11.15.0; syntax-reference.html lists 27 native types and no BPMN), and recent releases (Venn, Ishikawa, TreeView, Wardley) show the project is actively accepting new community-contributed diagram types via the `-beta` convention — but every new diagram landed since v11.13.0 ships a Langium grammar, parser, D3 renderer, getStyles, unit tests, E2E tests, and an entry in `@mermaid-js/examples`. That is the bar.
- **The competing upstream proposal (issue #7699 by Andreas Emrich, DFKI, opened May 2, 2026, "Add Native BPMN 2.0 Support to Mermaid.js," labeled Status: Triage / Type: Enhancement / Type: New Diagram, still open) creates real schedule pressure**: ship the external plugin first, get adoption, then file a Langium-backed upstream PR that out-executes the XML-heavy alternative. The strategy as written is correct; only the execution sequencing needs tightening.

## Details

### 1. Executive Summary

The "BPMN for Mermaid" project's locked direction is, on the whole, compatible with Mermaid's official directives. The architectural choices — ship as an external plugin first, adopt the `-beta` naming convention, write a from-scratch D3/SVG renderer with no bpmn-js runtime dependency, integrate Mermaid's theming via `getStyles(options)`, integrate accessibility via `commonDb`, and own pool/lane layout rather than abuse flowchart subgraphs — each map onto documented Mermaid patterns and recent (v11.13.0–v11.15.0) precedent for community-contributed diagrams.

Two compliance gaps and one stylistic mismatch require action before any upstream PR is opened:

1. **(Hard, for upstream)** The hand-written line-by-line parser is acceptable for the external-plugin v0/v1 release. It is **not acceptable for upstream submission.** Mermaid's official "Adding a New Diagram" page now references only Langium PRs as templates, the JISON variant of the same page is explicitly titled "(Deprecated)," and the project's own Langium-based `@mermaid-js/parser` package reached v1.0.0 on Feb 17, 2026 (upgrading to Langium v4, PR #7377 by @aloisklink).
2. **(Soft, can ship as-is)** The aria-roledescription key `BPMNDiagram` is technically defensible by analogy with the docs' example of `UMLDeploymentDiagram`, but `bpmnDiagram` is the camelCase form that more cleanly matches the docs' second recommended example (`deploymentDiagram`) and that matches how Mermaid's own diagram type keys are written in the codebase (`sequenceDiagram`, `classDiagram`, `stateDiagram`, `gitGraph`, etc.).
3. **(Strategic)** The competing upstream proposal in issue #7699 ("Add Native BPMN 2.0 Support to Mermaid.js," opened by andreas-emrich on May 2, 2026, labeled `Status: Triage`, `Type: Enhancement`, `Type: New Diagram`, still open) creates a real risk of the Mermaid team converging on a different, more XML-heavy DSL before this project's upstream PR lands. The mitigation is sequence: ship the external plugin in weeks, demonstrate adoption, and propose upstream with a Langium grammar and visible community traction.

### 2. Contribution-Process Compliance

The official "Adding a New Diagram/Chart" page at mermaid.ai/open-source/community/new-diagram.html (the single most authoritative source for this audit) lists exactly three numbered steps in its current form:

- **Step 1 — Grammar & Parsing**: "Please refer to the following PRs on how to use Langium to add a new diagram grammar," followed by two PR links (#4839, #4751). Langium is referenced exclusively. JISON appears nowhere on this page.
- **Step 2 — Rendering**: "Write a renderer that given the data found during parsing renders the diagram. To look at an example look at sequenceRenderer.js rather than the flowchart renderer as this is a more generic example. Place the renderer in the diagram folder."
- **Step 3 — Detection of the new diagram type**: "Add the capability to detect the new diagram to type to the detectType in `diagram-api/detectType.ts`. The detection should return a key for the new diagram type. This key will be used to as the aria roledescription, so it should be a word that clearly describes the diagram type."

Plus the four "Common parts": Directives, Accessibility (`commonDb` import shown verbatim), Theming (`getStyles(options)` in a `styles.js` under `src/diagrams/<your-diagram>/`), and Comments. Plus an `@mermaid-js/examples` package contribution: "Each diagram should have at least one example, and that should be marked as default."

The page itself carries a `WARNING: The below steps are a work in progress and will be updated soon` banner, meaning some specifics (especially around the external-diagram registration API and Langium scaffolding) are likely out of date relative to v11. The release notes are the more authoritative source for current practice.

The external-plugin-first strategy is fully supported. Mermaid exposes `mermaid.registerExternalDiagrams(diagrams: ExternalDiagramDefinition[], opts?: { lazyLoad?: boolean })` as a public v11 API (defined in `packages/mermaid/src/mermaid.ts`), and `ExternalDiagramDefinition` (defined in `packages/mermaid/src/diagram-api/types.ts:104`) requires exactly three fields: `id: string`, `detector: DiagramDetector`, `loader: DiagramLoader`. The historical mindmap plugin and the current `@mermaid-js/mermaid-zenuml` plugin are the canonical templates — both ship as separate npm packages and are wired in by user code via `await mermaid.registerExternalDiagrams([zenuml])`.

The official "Questions and Suggestions" page is brief and only directs proposers to (1) search existing issues/discussions and (2) open a new issue using the GitHub issue templates. There is no documented "RFC" or design-doc requirement. Issue #7699 is the de facto venue for the BPMN debate, and the project should engage there before opening a PR.

**Project alignment**: ✅ External-plugin-first matches API. ✅ Eventual upstream PR matches process. ⚠️ Engage on issue #7699 before opening a competing PR.

### 3. Grammar / Parser Compliance

JISON is dead for new diagrams. This is the single hardest constraint in this audit.

Evidence:
- The current `new-diagram.html` page mentions only Langium and links only to Langium PRs.
- A separate `new-diagram-jison.html` page exists with the title **"Adding a New Diagram/Chart (Deprecated)"** and an opening note: *"JISON grammars are deprecated in mermaid. Please use Langium instead. See New Diagram for more information. New diagrams with JISON grammars will not be accepted."*
- The `@mermaid-js/parser` Langium-based package shipped v1.0.0 on Feb 17, 2026, upgrading to Langium v4 (PR #7377 by @aloisklink) — a major change with breaking impacts (generated AST type names moved from `<typeName>` to `<typeName>.$type`; Langium now requires TypeScript ≥ 5.8.0).
- Recent new-diagram PRs (PR #7530 for usecase diagrams, May 2026) include explicit reviewer feedback, verbatim from the PR thread: *"Hi, I looked through your PR and it already seems very well advanced. The main adjustment I can see is the parser side: since Mermaid is adopting Langium for new diagrams, it may make sense to migrate this from Jison to Langium to match the current repository standard. Would you be open to a PR against your branch to help with that migration?"*

**Project alignment**:
- For the **external plugin (v0/v1)**: a hand-written line-by-line parser is fine. The `ExternalDiagramDefinition` API does not constrain the parser's internal implementation; it only requires that the diagram expose a `parser` with a `.parse(text)` method (typically wired via `parser.yy = db`). The project's hand-written parser is acceptable here. **Free choice.**
- For **upstream inclusion**: the hand-written parser must be ported to Langium. The project's plan to do this is correct. **Hard requirement.**

Recommendation: write the Langium grammar in parallel with the external-plugin v1 release rather than as a v2 follow-up. The `@mermaid-js/parser` package is the single shared Langium home for new diagrams; the BPMN grammar should land there as a new module mirroring how `pie`, `info`, and `gitGraph` are organized.

### 4. Detector / aria-roledescription Compliance

The new-diagram page states: *"The detection should return a key for the new diagram type. This key will be used to as the aria roledescription, so it should be a word that clearly describes the diagram type. For example, if your new diagram uses a UML deployment diagram, a good key would be 'UMLDeploymentDiagram' because assistive technologies such as a screen reader would voice that as 'U-M-L Deployment diagram.' Another good key would be 'deploymentDiagram' because that would be voiced as 'Deployment Diagram.' A bad key would be 'deployment' because that would not sufficiently describe the diagram."*

`BPMNDiagram` is defensible: BPMN is an initialism (Business Process Model and Notation), so the all-caps form parallels `UMLDeploymentDiagram` more than `deploymentDiagram`. Screen readers will voice this as "B-P-M-N Diagram," which is exactly the intended pronunciation.

However, looking at the codebase conventions for the actual detector keys (`sequenceDiagram`, `classDiagram`, `stateDiagram`, `erDiagram`, `gitGraph`, `flowchart`, `quadrantChart`, `xyChart`, `c4`, `architecture`, `mindmap`, `timeline`, `treemap`, `kanban`, `packet`, `radar`, `sankey`, `wardley`, `venn`, `ishikawa`, `treeView`), every detector key starts with a lowercase letter. The all-caps `BPMN` prefix would be the only outlier.

**Verdict**: **Soft mismatch.** `bpmnDiagram` is more consistent with codebase conventions while still satisfying the docs' explicit rule that the key be a real, screen-reader-friendly word. The DSL keyword can remain `bpmn-beta` (matching architecture-beta, wardley-beta convention) while the detector key / aria-roledescription is `bpmnDiagram`. Note the docs explicitly state the two need not match: *"the diagram type key does not have to be the same as the diagram keyword chosen for the grammar."*

### 5. Rendering, Layout, and the External-Diagram API

**Rendering**: a hand-written D3/SVG renderer with no bpmn-js runtime dependency matches what every recent native diagram does. Wardley Maps (v11.14.0) ship a D3.js renderer; Venn and Ishikawa (v11.13.0) ship parser + D3 renderer + tests; architecture-beta uses D3 with fcose for layout. Mermaid actively avoids heavyweight third-party rendering dependencies — the v11.0 work explicitly moved ELK out of the core bundle into `@mermaid-js/layout-elk` (current latest version 0.2.1, last published April 2026, per npm) to optimize size. The project's ~200KB ceiling is in the spirit of this practice.

**Layout**: the official Layouts page lists four supported engines — `elk`, `tidy-tree`, `cose-bilkent`, `dagre` — and the layout-loader mechanism is `mermaid.registerLayoutLoaders(elkLayouts)`, lazy-loaded so heavy engines aren't paid for unless used. The page's "Layout and look" section in syntax-reference.html notes: *"Currently, this is supported for flowcharts and state diagrams, with plans to extend support to all diagram types."* — meaning the global `layout: elk` / `look: handDrawn` knobs are NOT yet wired into most diagrams, and a new diagram is fully entitled to own its own layout. Architecture-beta exposes its own fcose-based knobs; sequence diagrams have always owned their layout. Wardley v11.14.0 explicitly notes: *"Handdrawn/rough mode (look: handDrawn) is not currently supported for Wardley Maps."*

The project's "coordinate-hint hybrid" — deterministic row-major auto-placement within lanes plus optional explicit coordinate hints — is therefore on-pattern. The decision to NOT delegate pool/lane layout to flowchart's subgraph engine is also defensible; flowchart subgraph direction handling has known issues (e.g., PR #6989 in v11.13.0 fixed parsing where `direction TD` was not recognized within subgraphs), and pool/lane semantics genuinely differ from generic clusters.

**Whether to adopt ELK**: ELK can produce excellent hierarchical layouts for BPMN's typical horizontal swimlane structure, but ELK is shipped as a separate plugin (`@mermaid-js/layout-elk@0.2.1`, last published April 2026) and is NOT registered by default. A BPMN external plugin that hard-depends on ELK would force end users to also `registerLayoutLoaders(elkLayouts)`. The cleanest path is:
- Ship the custom coordinate-hint layout as the default.
- Optionally accept `layout: elk` if the user has registered ELK, falling back to the custom layout otherwise (this is how flowchart degrades gracefully when ELK is not registered).

**External-diagram API**: the `ExternalDiagramDefinition` shape (`{ id, detector, loader }`) is minimal and explicitly accepts an async `loader` that returns the full DiagramDefinition (`{ db, parser, renderer, styles, init? }`). The project's split — separate BpmnDb, parser, renderer, and getStyles modules — maps cleanly onto this. No conflict.

### 6. Theming Compliance

The new-diagram page mandates: *"The entry point for the styling engine is in src/styles.js. The getStyles function will be called by Mermaid when the styles are being applied to the diagram. This function will in turn call a function your diagram should provide returning the css for the new diagram."* with a sample:

```js
const getStyles = (options) =>
  `
    .line {
      stroke-width: 1;
      stroke: ${options.lineColor};
      stroke-dasharray: 2;
    }
    `;
```

The five theme variables the project proposes to consume (`lineColor`, `mainBkg`, `nodeBorder`, `clusterBkg`, `textColor`) all appear in the theming.html documentation:
- `lineColor` — base theme variable, "calculated from background."
- `mainBkg` — base theme variable, "Background in flowchart objects like rects/circles, class diagram classes, sequence diagram etc."
- `nodeBorder` — listed under "Flowchart Variables," default = `primaryBorderColor`, description: "Node Border Color."
- `clusterBkg` — listed under "Flowchart Variables," default = `tertiaryColor`, description: "Background in subgraphs."
- `textColor` — base theme variable, "Text in diagram over the background for instance text on labels and on signals in sequence diagram or the title in Gantt diagram."

These are valid and well-chosen for BPMN's needs (lanes are essentially clusters; tasks are nodes; sequence flows are lines; labels need textColor). Replacing the prototype's Tailwind-based styling with `getStyles(options)` is correct.

One consideration: an external plugin cannot register itself into `themes` in core's `src/styles.js`. That registration happens automatically when an `ExternalDiagramDefinition` is loaded — the loader-returned `DiagramDefinition` includes a `styles` function that gets wired into the theming pipeline at runtime. The project's plan to expose `getStyles(options)` directly is correct; no extra plumbing needed for the external-plugin phase.

**Project alignment**: ✅ correct theme variable names, ✅ correct function signature, ✅ correct wiring path.

### 7. Icons Compliance

The icons page documents `mermaid.registerIconPacks([{ name, loader }])` for Iconify-style packs (200,000+ icons from icones.js.org). The mechanism is used today **only by architecture-beta** to render service icons inside group/service boxes. No other diagram in core currently consumes the icon pack system.

BPMN task-type markers (user, service, script, send, receive) and event markers (message, timer, error) are visual decorations, not user-supplied icons. The BPMN 2.0 spec defines specific shapes and positions for each marker. Hand-drawing these as SVG paths inside the renderer (the way sequence diagram arrow heads are drawn, or the way the architecture-beta junction is drawn) is the correct approach.

Using `registerIconPacks` for built-in BPMN markers would be wrong on two counts: (a) it would force users to register an icon pack just to get standard BPMN markers, and (b) it would expose Iconify naming concerns (prefix collisions, version pinning) to BPMN authors who only want spec-compliant markers.

**Verdict**: hand-drawn SVG for BPMN markers is correct. The icon pack system is a **free choice**, available if the project ever wants to allow users to put third-party icons inside BPMN tasks (e.g., a `task[User Login](logos:auth0)` syntax later), but unnecessary for the v1 scope.

### 8. Accessibility Compliance

The new-diagram page documents accessibility as one of the "common parts" with three required pieces:
1. **aria-roledescription** — auto-injected from the detector key (see §4).
2. **Accessible title** via `accTitle: ...` — wired through `setAccTitle/getAccTitle` imported from `commonDb`.
3. **Accessible description** via `accDescr: ...` (single-line or multi-line block) — wired through `setAccDescription/getAccDescription` imported from `commonDb`.

The exact import the docs show:

```js
import {
  setAccTitle,
  getAccTitle,
  getAccDescription,
  setAccDescription,
  clear as commonClear,
} from '../../commonDb';
```

The project plans to do exactly this. **Aligned, no changes needed.** Note: in an external plugin, the import path will be different (e.g., `from 'mermaid'` re-exported, or via the `init` callback's `commonDb`); the internal-relative path shown above is for in-tree contributions. Confirm the public re-export at plugin-development time — at the time of this writing, `commonDb` is not part of mermaid's documented public API surface, so the safest pattern in the external plugin is to have BpmnDb expose its own `setAccTitle/setAccDescription` shims and rely on `commonClear` only after upstream merge.

### 9. Naming / Versioning Compliance

The `-beta` suffix is the documented pattern for new diagram types in Mermaid v11. Live examples from the syntax-reference sidebar (and confirmed in release notes):

- `architecture-beta` — added in v11.1.0
- `xychart-beta` — added pre-v11
- `kanban-beta`, `packet-beta`, `radar-beta` — added during v11.x
- `treemap-beta` — added in v11.x
- `venn-beta` — added in v11.13.0 (GitHub tag dated March 9, 2026; Atlassian Mermaid for Confluence changelog confirms the library bump on 2026-03-14; the official mermaid.ai blog post announcing v11.13.0 is dated 20 April 2026)
- `ishikawa-beta` — added in v11.13.0
- `treeView` (note: no `-beta` suffix here, exception) — added in v11.14.0
- `wardley-beta` — added in v11.14.0 (last-published date April 1, 2026 per the npm registry)
- `eventmodeling` — added during v11.x (no `-beta` in current sidebar)

The convention is overwhelmingly `<keyword>-beta`. `bpmn-beta` is the correct choice. **Aligned.**

The bpmn-beta project should study `packages/mermaid/src/diagrams/wardley/` as the canonical reference layout.

New diagrams that own their layout (Wardley, architecture-beta, ishikawa-beta) opt out of this system entirely. The BPMN plugin following the same pattern is consistent with current practice.

### 12. Net Recommendations (prioritized)

**Must-do for upstream PR acceptance (hard requirements):**

1. **Port the parser to Langium before opening the upstream PR.** Land the BPMN grammar inside `@mermaid-js/parser` as a sibling of the existing `pie`, `info`, `gitGraph` Langium grammars. Use the `@mermaid-js/parser@1.0.0` Langium v4 baseline. Reference: PRs #4839 and #4751 (linked from the new-diagram doc page) and PR #7530's reviewer feedback on parser standards.
2. **Lower the detector key from `BPMNDiagram` to `bpmnDiagram`** to match the codebase convention used by every other detector key (sequenceDiagram, classDiagram, stateDiagram, …). The DSL keyword `bpmn-beta` stays unchanged.
3. **Ship a `getStyles(options)` function in `styles.js`** keyed off the documented theme variables (lineColor, mainBkg, nodeBorder, clusterBkg, textColor, plus secondaryColor for pool headers and primaryBorderColor for default node borders). Drop all Tailwind from the renderer; theming must flow from Mermaid's themeVariables.
4. **Add at least one example to `@mermaid-js/examples` package** as the default, plus 2–3 more covering pool/lane, gateway types, and message flows. Required by the new-diagram doc page.
5. **Provide unit tests + Cypress E2E tests + Argos visual regression baselines**, matching the precedent in v11.13.0 (Venn/Ishikawa) and v11.14.0 (Wardley) PRs.
6. **Documentation page** at `packages/mermaid/src/docs/syntax/bpmn.md`, matching the level of detail of `architecture.md` and `wardley.md` (syntax reference, examples, theming notes, known limitations).

**Should-do for the external-plugin v1 release (soft, recommended):**

7. **Confirm the `commonDb` exposure path before the plugin ships.** Either re-implement `setAccTitle/setAccDescription/clear` locally in BpmnDb (safest), or pin a runtime mermaid version known to re-export the helpers. Drop in the in-tree relative import only at the moment of the upstream PR.
8. **Consider ELK as an optional layout engine** for the upstream version: detect whether `registerLayoutLoaders` has been called for ELK and fall back to the coordinate-hint layout otherwise. This mirrors how flowchart degrades when ELK is not registered.
9. **Adopt architecture-beta-style edge-side hints** (`t2:R ~~> L:t3`) for cross-pool message flows. The project's intent here matches architecture-beta directly — no risk, only payoff.
