## STRATEGIC CONTEXT

This project has been re-scoped through a multi-model Council evaluation
(Claude + ChatGPT Deep Research). The outcome is a hybrid specification
called BP-SKILL: Business Process Agent Skill Suite.

The operating model is:

```
The playground is for people.
The skills are for agents.
The prompt packs are the universal fallback.
The repos are the source of truth.
The Repls are the manufacturing floor.
```

The architecture has three permanent layers:

```
LAYER 1 — DISCOVERY
BABOK v3-aligned intake, elicitation, stakeholder mapping.
Produces: Process Intake Record (PIR), stakeholder register.

LAYER 2 — NARRATIVE
Process Narrative Specification (PNS) — the canonical handoff
artifact that every skill consumes and enriches. Structured to
satisfy ISO 9001 §4.4.1 process-box semantics, BABOK Core Concept
Model anchoring, and IEEE/ISO/IEC 29148:2018 information discipline.

LAYER 3 — VISUAL AND DECISION MODELING
bpmn-beta (OKHP3 prototype DSL) as the visual output layer.
DMN 1.4 for externalised decision logic when warranted.
```

BP-SKILL extends the Agent Skills open standard (agentskills.io).
It does NOT alter SKILL.md syntax. It standardises a 15-skill array,
a 9-file variable layer, and the PNS handoff contract on top of the
base format.

#### SKILL 01 — process-intake-and-scope

status: core
standards_refs:

- “BABOK v3 §3.1–3.4 (Business Analysis Planning and Monitoring)”
- “BABOK v3 §6.1 (Strategy Analysis)”
- “BPM CBOK v4.0 Phase 1 (Alignment to Strategy and Goals)”
- “APQC PCF v7.4 (taxonomy classification)”
  consumes: request brief, organization-profile.md, optional process-taxonomy.md
  produces: PNS.md [status: draft-intake], pir.yaml

Purpose: Establish the process candidate, request type, sponsor,
business objective, in-scope and out-of-scope boundaries, urgency,
target audience, and initial APQC PCF taxonomy placement.

Trigger conditions: Any new request to discover, document, improve,
audit, hand off, or publish a business process.

Workflow stages:

1. Classify the request type (new documentation, improvement,
   audit, handoff, or transformation).
1. Assign a stable process_id.
1. Declare scope boundary (in/out/deferred).
1. Bind applicable context files from context/ tree.
1. Map to APQC PCF v7.4 hierarchy and element ID.
   Dual-tag to v8.0 if available (SHOULD per BP-SKILL §taxonomy).
1. Initialise evidence register and open-issues register.
1. Set PNS.md status to draft-intake.

SKILL.md body MUST include:

- Purpose
- Trigger conditions
- When NOT to use
- Classification decision logic
- APQC taxonomy binding rules (including dual-tag instruction)
- PIR output schema
- Handoff instruction: “Proceed to stakeholder-and-role-mapping”

#### SKILL 03 — elicitation-and-interview-facilitation

status: core
standards_refs:

- “BABOK v3 §4 (Elicitation and Collaboration)”
- “BABOK v3 Technique §10.25 (Interviews)”
- “BABOK v3 Technique §10.50 (Workshops)”
- “BABOK v3 Technique §10.18 (Document Analysis)”
- “BPM CBOK v4.0 KA 3 (Process Analysis)”
  consumes: PNS.md [scoped], stakeholder register, sector-context.md
  produces: PNS.md [status: elicited], evidence-enriched with source
  attribution, assumptions, confidence level, follow-up questions

Purpose: Run structured discovery interviews, workshops, or
observation-guided sessions that surface the actual process,
not the idealised one.

CRITICAL DESIGN CONSTRAINT: Encode BABOK elicitation logic as
conditional branching, not just a checklist.
- If trigger is ambiguous → generate clarifying scoping questions
- If roles span departments → probe handoff and approval logic
- If process crosses systems → capture interface and data-flow notes
- If contradictions surface → flag as open issue, do not resolve silently
- If evidence is thin → lower confidence score and flag for follow-up

Workflow stages:

1. Generate a question plan from the PNS scope and stakeholder register.
1. Execute or simulate elicitation script using conditional branching.
1. Capture evidence with source attribution (interview ID, document ID).
1. Record contradictions as open issues, not resolved facts.
1. Set confidence level per process section (high / medium / low).
1. Update PNS.md with evidence and set status to elicited.

SKILL.md body MUST include:

- Purpose, triggers, when NOT to use
- Conditional elicitation branching logic (the interrogation engine)
- Evidence attribution format
- Contradiction handling rules
- Confidence scoring rubric
- Handoff instruction: “Proceed to as-is-process-capture”

#### SKILL 10 — process-validation-and-quality-scoring

status: core
standards_refs:

- “BABOK v3 §5 (Requirements Life Cycle Management — verify/validate)”
- “ISO 9001:2015 §4.4.1”
- “IEEE/ISO/IEC 29148:2018 (good-requirement characteristics)”
  consumes: PNS.md [modeled or analyzed], BPMN/DMN artifacts if present,
  all context files, validation rubric
  produces: quality scorecard (0–100), defect list,
  approval recommendation, PNS.md validation state update

Validation rules V1–V9:
V1  Schema completeness — all 13 required sections present
V2  Traceability — activities trace to evidence; rules trace to activities
V3  Role coverage — one Accountable per activity; all roles in dictionary
V4  Singular activity statements (IEEE 29148 good-requirement rule)
V5  Verifiable KPIs — formula + data source present
V6  Exception coverage — every gateway outcome has an exception path
V7  Control coverage — controls referenced or explicitly waived per step
V8  BPMN/DMN traceability — every model element traces to a PNS ID
V9  No open questions marked must_resolve=true remain unresolved

V1–V7 failures → non-conformant; cannot proceed to publication.
V8–V9 failures → warnings; may proceed if score ≥ publication threshold
defined in compliance-controls-registry.md.

Quality score bands:
90–100: Ready for publication
75–89:  Conditional — resolve V8/V9 items
50–74:  Requires remediation before publication
< 50:   Return to narrative authoring

Then Markdown body with:

One fully populated example instance

### context/organization-profile.md

Required: company_name, industry (NAICS code), size_tier,
operating_regions, regulatory_environment[], process_maturity_level
(CMMI 1–5 or APQC PEMM 1–5), business_units_in_scope[]
Optional: strategy_themes[], customer_segments[], sourcing_model,
risk_appetite, naming_conventions, document_retention_policy
Usage: intake, future-state, validation, controls, and publication
skills MUST read before making enterprise-level assumptions.

### context/sector-context.md

Required: sector_name, domain_vocabulary{}, applicable_standards[],
common_process_patterns[], sector_apqc_mapping{pcf_version, ids[]}
Optional: common_exception_patterns[], benchmark_kpis[],
sector_glossary_deltas{}, industry_acronyms{}, policy_archetypes[]
Usage: elicitation, narrative, modeling, validation, and publication
SHOULD normalise industry terminology against this file.

### context/regional-context.md

Required: jurisdictions[] (ISO 3166-1), primary_language (BCP 47),
secondary_languages[], regulatory_bodies[], compliance_frameworks[],
date_format (RFC 3339 default), currency_code (ISO 4217),
measurement_system
Optional: timezone (IANA), working_week, public_holidays_ref,
privacy_data_residency_notes, local_approval_norms
Usage: skills producing externalised documents or regionally
constrained controls MUST honour this file.

### context/role-dictionary.md

Required per role: role_id (stable opaque), display_name,
display_name_aliases[], responsibilities[], authority_level
(executive | senior_manager | manager | individual_contributor
| external), raci_default{activity_pattern → R/A/C/I},
system_access_profile[]
Optional: reports_to_role_id, delegates_to_role_id[], headcount,
separation_of_duties_flags[], approval_limits{}
Usage: stakeholder, RACI, SOP, validation, and publication skills
MUST use canonical role IDs from this file. Any role not in the
dictionary MUST be declared as provisional.

### context/process-taxonomy.md

Required: taxonomy_name, taxonomy_version, apqc_version,
hierarchy{}, internal_naming_rules, ownership_structure[]
APQC DUAL-TAGGING RULE: If taxonomy references are to APQC PCF v7.x,
implementations SHOULD also store the v8.0 equivalent ID when
available, to prevent migration lock-in. Both IDs stored as:
apqc_v74_id: “3.0”
apqc_v80_id: “3.0.1”  # if known
Optional: capability_map_ref, value_stream_map_ref,
legacy_process_aliases{}, portfolio_tags[]
Usage: intake, SIPOC, publication, and cross-process reporting MUST
use this file for classification.

### context/notation-preferences.md

Required: primary_notation (bpmn_2_0_2 | cross_functional_flowchart
| value_stream_map | swimlane_simple), secondary_notations[],
renderer_targets[] (mermaid_bpmn_beta | bpmn_xml | drawio |
bpmnio_json | graphviz), output_formats[], theme_defaults{}
Optional: color_palette, font_family, accessibility_requirements[],
max_pool_count, max_lane_count_per_pool, gateway_label_convention
Usage: visual and decision-model skills MUST consult before generating
renderable diagrams. Canonical BPMN/DMN source artifacts are always
preferred even when alternate renderers are requested.

mandatory_approval_gate (bool), evidence_requirements[],

## PROCESS NARRATIVE SPECIFICATION (PNS) — CANONICAL HANDOFF ARTIFACT

### Status lifecycle (9 states — normative)

Every PNS.md transition through these states MUST be sequential.
Skills MUST NOT advance PNS.md status beyond their own output state.
Implementations MAY add sub-status values but MUST NOT skip
the distinction between current-state capture and validated publication.

```
draft-intake         → set by: process-intake-and-scope
scoped               → set by: stakeholder-and-role-mapping
elicited             → set by: elicitation-and-interview-facilitation
documented-as-is     → set by: as-is-process-capture
modeled              → set by: process-narrative-authoring
analyzed             → set by: process-gap-and-exception-analysis
validated            → set by: process-validation-and-quality-scoring
packaged             → set by: publication-and-handoff-packaging
published            → set by: publication-and-handoff-packaging
                               (after approval gate clears)
```

```yaml
---
artifact_type: process-narrative-specification

  - standard: APQC-PCF
    version: "7.4"
    hierarchy_id: ""
    element_id: ""               # stable 5-digit APQC element ID
    v80_id: ""                   # dual-tag SHOULD field
context_refs:                    # files from context/ that apply
  - context/organization-profile.md

babok_core_concepts:
  change: ""
  need: ""
  solution: ""
  stakeholders: []
  value: ""
  context: ""

```

## 19. APQC PCF Taxonomy Position

### PNS Traceability rules (non-negotiable)

```
- Every process step MUST have a stable step ID (act-001, act-002…)
- Every referenced role MUST exist in role-dictionary.md or be
  declared provisional
- Every control MUST reference a control_id when registry is present
- Every BPMN task, event, and gateway MUST trace back to a step ID
- Every DMN decision MUST trace back to a decision point ID or rule
- Every SOP procedure step MUST cite its source PNS step ID
- Every publication bundle MUST embed the exact PNS.md version it
  was derived from
```

## UNIVERSAL CONSTRAINTS

```
- No BFS, Builders FirstSource, employer-owned examples,
  employer colors, or employer references anywhere

- No telemetry
- No changes to production React app behavior except README
  and documentation links

  native Mermaid core, production plugin, executable BPMN,
  BPMN XML round-trip, or full BPMN 2.0 conformance

  never invented syntax like task("Label")@{ type: "userTask" }

  Alignment to Strategy and Goals → Architect Changes →
  Develop Initiatives → Implement Changes →
  Measure Success / Benefits Realisation

  Plan / Analyze / Design / Implement / Monitor / Optimize
- APQC PCF element IDs (five-digit) are stable identifiers;
  hierarchy IDs can change across versions; always version-tag
```
