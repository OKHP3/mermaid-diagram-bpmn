## 2. Best-of decisions

### Decision 1 — Use `/skills/`, not `/skill/`

The Agent Skills spec defines a skill as a directory containing `SKILL.md`, with optional `scripts/`, `references/`, and `assets/` directories. ([Agent Skills][3]) Use:

```text
skills/okhp3-mermaid-theme-builder/
skills/okhp3-bpmn-for-mermaid/
```

Do **not** use:

```text
skill/
```

Singular `skill/` is not fatal, but it is less scalable and less aligned to multi-skill repo conventions.

### Decision 2 — Use specific OKHP3 names

Use:

```yaml
name: okhp3-mermaid-theme-builder
name: okhp3-bpmn-for-mermaid
```

Not:

```yaml
name: mermaid-theme
name: bpmn-for-mermaid
```

Reason: `mermaid-theme` is clean but too generic. `okhp3-mermaid-theme-builder` and `okhp3-bpmn-for-mermaid` are more discoverable, defensible, and brand-scoped. The Agent Skills spec requires names to be lowercase, hyphenated, max 64 characters, and match the parent directory. ([Agent Skills][3])

### Decision 3 — Keep `SKILL.md` lean

The spec recommends splitting longer content into referenced files and keeping the main `SKILL.md` under 500 lines; metadata and description stay loaded for discovery, full instructions load on activation, and resources load only as needed. ([Agent Skills][3])

So:

```text
SKILL.md = routing + workflow + output rules
references/ = deep docs
assets/ = machine-readable registries
scripts/ = deterministic helpers
tests/ = proof it works
```

### Decision 4 — Include scripts, but keep them local and deterministic

Proposal A’s instruction-only approach is safe, but underpowered. Proposal B’s script/test structure is better. Proposal C’s script ideas are useful, but should be implemented as `.mjs` modules with fixtures and tests rather than ad hoc one-off files. 

### Decision 5 — BPMN must be “prototype DSL,” not “Mermaid 11.15 shipped syntax”

Your repo says Mermaid has a BPMN gap and that the credible path is a dedicated `bpmn-beta` plugin, later proposed upstream after syntax stabilizes. ([GitHub][4]) Your project page also says this is not executable BPMN, not XML round-tripping, not full BPMN 2.0 conformance, and not yet a production Mermaid plugin. ([OverKill Hill P³™][1])

That language must govern the skill.

```text
gateway("Decision")@{ type: "exclusive" }
event("Start")@{ type: "startEvent", trigger: "none" }
```

Your current DSL is:

```text
task:user t1 "Review Request"
xor g1 "Approved?"
start s1 "Request Raised"
```

The current public BPMN page and GitHub README use that text-first syntax. ([OverKill Hill P³™][1])

## Do not stuff full reference manuals into `SKILL.md`

Move long material into:

```text
references/
assets/
examples/
```

That is exactly what progressive disclosure is for. ([Agent Skills][3])

## Do not make scripts the only source of truth

The skill must remain useful even when a host cannot execute local scripts. Scripts are accelerators. `SKILL.md` plus curated references are the durable interface.

---

# 6. Final operating model

Use this internal positioning everywhere:

```text
The apps are for people.
The skills are for agents.
The prompt packs are for everyone else.
The repos are the source of truth.
The Repls are the manufacturing floor.
```

That keeps the architecture clean and the brand story intact.
