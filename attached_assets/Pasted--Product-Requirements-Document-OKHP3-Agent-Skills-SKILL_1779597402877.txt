## 1. Executive Summary

This document defines the requirements, file structure, and complete content for two SKILL.md companion deliverables — one for each of the two OverKill Hill P³ React/Tailwind/TypeScript applications currently hosted on GitHub Pages and Replit. Each skill packages the logic, vocabulary, rules, and export behavior of its parent application into a headless, agent-consumable format that any SKILL.md-compatible platform can load and execute without the UI.

The practical effect: users working inside Claude, Claude Code, GitHub Copilot, Cursor, VS Code, Gemini CLI, OpenAI Codex, or any other adopting platform can trigger Mermaid theming or bpmn-beta generation natively inside their existing workflow, with no browser tab required. The visual tools remain the primary demonstration and trust surface. The skills become the distribution layer.

**Skills to produce:**

| Skill | Parent Application | Trigger Domain |
|---|---|---|
| `mermaid-theme` | Mermaid Theme Builder | Diagram theming, palette application, prompt scaffold export |
| `bpmn-for-mermaid` | BPMN for Mermaid | Business process to bpmn-beta DSL generation and validation |

**Delivery model:** Each skill lives inside its existing GitHub repository under a `skills/` subfolder. No new repositories required. Each skill is self-contained and independently discoverable.

## 2. Background and Context

### 2.1 Parent Applications

**Mermaid Theme Builder** (`github.com/OKHP3/mermaid-theme-builder`) is a browser-only React + Vite + Mermaid.js visual governance utility. Its core loop is: paste Mermaid code, detect diagram family, apply a named palette, preview live across diagram types, and export as a `themeVariables` block, a Markdown style bootstrap, or an LLM prompt scaffold. It ships four built-in palettes (Ocean Depth, Forest Sage, Slate Ember, Violet Mist) and four brand presets (OKH P³, Glee-fully, AskJamie, Neutral Enterprise). It is 100% client-side, MIT licensed, and currently at v0.3 with v0.5 on the active roadmap.

**BPMN for Mermaid** (`github.com/OKHP3/mermaid-diagram-bpmn`) is a Mermaid-native `bpmn-beta` diagram type proposal. Its core proposition is a clean DSL that maps BPMN 2.0 Descriptive Conformance subset elements (start/end events, tasks, gateways, sequence flows, pools, lanes) into Mermaid-style text syntax. It targets: AI-generatability, Git-native storage, readable-without-tooling, and correct BPMN visual notation without bpmn-js. Currently prototype-stage with a hand-written parser and SVG renderer.

### 2.2 Why Skills, Not Just the Apps

The browser tools solve the visual/interactive use case. They don't solve the in-agent use case. A practitioner working in Claude Code to document a business process has no way to pull the bpmn-beta DSL spec into context and produce valid output on first try. A team standardizing on a Mermaid palette has no agent-side mechanism to enforce that palette across generated diagrams in Cursor or GitHub Copilot. The skills bridge that gap without replacing or competing with the visual tools — they extend reach into toolchains where a browser tab is not the right answer.

### 2.3 What SKILL.md Provides

A SKILL.md is a folder containing one required file (the `SKILL.md` itself, with YAML frontmatter for machine-readable metadata and a Markdown body for agent instructions) and optional supporting subfolders: `references/` for documentation the agent loads on demand, `assets/` for templates and data files, and `examples/` for sample inputs and outputs. The agent reads only the frontmatter metadata at all times (for triggering) and loads the full body and supporting files only when the skill activates. This keeps context overhead near zero until the skill is needed.

### 4.4 Loading Behavior

Agents keep only the frontmatter in context at all times. The full Markdown body loads when the skill is triggered. Supporting files in `references/`, `assets/`, and `examples/` are loaded on demand when the body instructions reference them. This means the skill can bundle substantial reference material without imposing context cost until it's actually needed.

### 4.5 Triggering Behavior

The `description` field is the primary trigger surface. It must be written to match the natural language patterns a user would use when they need this capability. Agents pattern-match against the description to decide whether to load the skill. Verbs matter. Nouns matter. The description is not documentation — it is a routing instruction.

## Overview

This skill applies consistent visual theming to Mermaid diagram code. It identifies the diagram family, selects or constructs a palette, generates a complete Mermaid `themeVariables` configuration block, wraps the input diagram in the styled output, and optionally produces a Markdown style bootstrap or LLM prompt scaffold.

The output is platform-ready Mermaid code with embedded theming — not a description of what theming would look like.

## Workflow

Execute this workflow in order. Do not skip steps.

### Step 1 — Identify or Accept Input Diagram

If the user has provided Mermaid code, use it as-is. If they have described a diagram they want created, generate it first using standard Mermaid syntax, then proceed with theming.

If no diagram is present and none is described, ask for one before continuing.

### Step 2 — Detect Diagram Family

Read the first non-whitespace keyword after the opening code fence to determine the diagram family:

| Keyword(s) | Family | Theme Behavior |
|---|---|---|
| `flowchart`, `graph` | Flowchart | Full themeVariables support |
| `sequenceDiagram` | Sequence | Limited — themeVariables apply to actors and labels; some properties ignored |
| `classDiagram` | Class | Full themeVariables support |
| `gantt` | Gantt | Background and label colors apply; node fills do not |
| `erDiagram` | ER | Full themeVariables support |
| `stateDiagram-v2`, `stateDiagram` | State | Full themeVariables support |
| `pie` | Pie | Background and font apply; segment colors use internal rotation |
| `journey` | Journey | Label and background colors apply |
| `bpmn-beta` | BPMN (OverKill Hill P³) | Full themeVariables support via Mermaid Theme Integration |
| `mindmap` | Mindmap | Limited support — base colors only |
| `xychart-beta` | XY Chart | Full themeVariables support |

Note the family in your working context. The Sequence and Gantt families have reduced compatibility — flag this in your output.

#### Custom Palette

If the user provides specific colors (hex, HSL, RGB, or descriptive), construct a coherent palette by:

1. Treating the user's primary color as `primaryColor` and `mainBkg`
2. Deriving `primaryBorderColor` as a 15% darker variant
3. Setting `primaryTextColor` to white (#ffffff) for dark primaries, near-black (#1a1a1a) for light primaries — verify minimum 4.5:1 contrast ratio
4. Setting `secondaryColor` to a 30% lighter or hue-shifted variant of primary
5. Setting `tertiaryColor` to a complementary or analogous hue 60-120 degrees away
6. Setting `background` to a dark desaturated variant of primary for dark themes, or near-white (#f8f8f8) for light themes
7. Setting `lineColor` to a bright accent — often the tertiary at 20% more saturation
8. Setting `clusterBkg` to the background color darkened by 10%

State any derivation assumptions explicitly in your output.

Produce the complete configuration block in this format:

```javascript

  'theme': 'base',
  'themeVariables': {
    'primaryColor': '[value]',
    'primaryTextColor': '[value]',
    'primaryBorderColor': '[value]',
    'secondaryColor': '[value]',
    'secondaryTextColor': '[value]',
    'secondaryBorderColor': '[value]',
    'tertiaryColor': '[value]',
    'tertiaryTextColor': '[value]',
    'tertiaryBorderColor': '[value]',
    'background': '[value]',
    'mainBkg': '[value]',
    'nodeBorder': '[value]',
    'clusterBkg': '[value]',
    'clusterBorder': '[value]',
    'lineColor': '[value]',
    'edgeLabelBackground': '[value]',
    'fontFamily': '[value]',
    'fontSize': '[value]',
    'labelBackground': '[value]',
    'labelTextColor': '[value]',
    'titleColor': '[value]'
  }
}}%%
```

### Step 5 — Produce Styled Diagram Code

Prepend the `%%{init:...}%%` block to the user's Mermaid code. Output the complete, copy-paste-ready result inside a fenced Mermaid code block.

```
```mermaid
%%{init: { 'theme': 'base', 'themeVariables': { ... } }}%%
[original diagram code]
```
```

If the diagram family has reduced compatibility (Sequence, Gantt, Pie, Journey, Mindmap), include a one-line renderer note immediately after the code block:

> Renderer note: [Family] diagrams have partial themeVariables support. [Specific limitation]. Verify output in your target renderer.

### Step 6 — Export Options

Produce whichever exports the user requested, or all three if no specific export was requested.

**Export A: Standalone themeVariables JSON**

Produce a clean JSON object (no wrapping %%{init}%% syntax) for use in `mermaid.initialize()`:

```json
{
  "theme": "base",
  "themeVariables": {
    "primaryColor": "[value]",
    ...
  }
}
```

**Export B: Markdown Style Bootstrap**

A Markdown-embeddable block the user can paste before any diagram in a document to establish the theme:

```markdown
<!-- Mermaid Theme: [palette name] — OverKill Hill P³ -->
<!-- Apply this init block before each diagram or set globally in your Mermaid config -->

%%{init: { 'theme': 'base', 'themeVariables': { [all 21 variables] } }}%%
```

Include a usage note: "Paste this block immediately before each Mermaid code fence in Markdown documents. For site-wide application, pass the themeVariables object to `mermaid.initialize()` in your site's configuration file."

**Export C: LLM Prompt Scaffold**

A reusable prompt prefix that instructs any LLM to generate on-brand Mermaid diagrams on first try:

```
When generating Mermaid diagrams for this conversation, always include the following theme initialization block at the top of every diagram:

%%{init: { 'theme': 'base', 'themeVariables': { [all 21 variables] } }}%%

Rules:
- Always use 'theme': 'base' as the base theme. Never use 'default', 'dark', 'forest', or 'neutral'.
- Preserve all themeVariables exactly as provided. Do not substitute, approximate, or omit any variable.
- Place the %%{init}%% block on the first line of the Mermaid code, before the diagram type keyword.
- For flowchart diagrams, also add classDef definitions for any nodes that need semantic color differentiation beyond the base palette.
- Do not add inline style declarations that override themeVariables unless explicitly requested.
```

| Renderer | themeVariables | %%{init}%% block | Notes |

| Mermaid Live Editor (mermaid.live) | Full | Yes | Reference renderer |
| Mermaid.ai (mermaid.ai) | Full | Yes | Full init block support |
| GitHub Markdown | Partial | No | Strips %%{init}%%; uses GitHub's forced theme |
| GitLab Markdown | Partial | No | Similar to GitHub |
| Notion | None | No | Renders diagram only, no theming |
| Obsidian | Full | Yes | Best markdown renderer for theming |
| Confluence | Partial | Plugin-dependent | Check your Mermaid plugin version |
| VS Code preview | Full | Yes | With Mermaid extension |
| Docusaurus | Full | Yes | Via mermaid.initialize() config |
| VitePress | Full | Yes | Via markdown.mermaidOptions config |

When the user's target renderer is GitHub, GitLab, Notion, or Confluence, add a renderer advisory after the styled output: "Note: [renderer] does not support the %%{init}%% theming block. Your diagram will render with the platform's default theme. Use the themeVariables JSON export to configure theming at the application level if you have access to Mermaid initialization."

- Keep explanatory text minimal. The output is the product.

## Overview

This skill generates and validates `bpmn-beta` Mermaid diagrams — the OverKill Hill P³ BPMN-native diagram type for Mermaid. The DSL maps BPMN 2.0 Descriptive Conformance subset elements to a clean, text-first syntax that is readable by process analysts and generatable by LLMs without syntax repair.

The output is valid, copy-paste-ready bpmn-beta syntax inside a Mermaid code fence — not a description, not a flowchart approximation, not XML.

---

## DSL Reference

### Diagram Declaration

Every bpmn-beta diagram starts with:

```
bpmn-beta
```

Optional metadata on the following lines (before any pool or top-level elements):

```
accTitle: [Diagram title — used by screen readers and export tools]
accDescr: [Longer description — optional]
```

### Event Keywords

| Keyword | BPMN Element | Shape | Usage |
|---|---|---|---|
| `start` | Start event (none) | Thin circle | One per primary process path |
| `end` | End event (none) | Thick circle | One or more per lane |
| `event:message` | Message intermediate event | Circle + envelope | Sent/received messages |
| `event:timer` | Timer intermediate event | Circle + clock | Time-triggered steps |
| `event:error` | Error end event | Thick circle + lightning | Error termination |

Syntax:

```
start    [id]  "[label]"
end      [id]  "[label]"
event:message [id] "[label]"
event:timer   [id] "[label]"
event:error   [id] "[label]"
```

### Task Keywords

| Keyword | BPMN Element | Marker | Usage |
|---|---|---|---|
| `task` | Abstract task | Rounded rectangle | Generic step, type unspecified |
| `task:user` | User task | Person icon | Human-performed work |
| `task:service` | Service task | Gear icon | Automated/system step |
| `task:script` | Script task | Scroll icon | Script execution |

Syntax:

```
task         [id]  "[label]"
task:user    [id]  "[label]"
task:service [id]  "[label]"
task:script  [id]  "[label]"
```

### Gateway Keywords

| Keyword | BPMN Element | Shape | Routing |
|---|---|---|---|
| `xor` | Exclusive gateway | Diamond + X | One path only |
| `and` | Parallel gateway | Diamond + + | All paths simultaneously |
| `or` | Inclusive gateway | Diamond + O | One or more paths |

Syntax:

```
xor [id] "[label]"
and [id] "[label]"
or  [id] "[label]"
```

### Sequence Flow

All sequence flows use `-->`. Edge labels go after a colon on the same line:

```
[source-id] --> [target-id]
[source-id] --> [target-id]: "[condition label]"
```

Labels on gateway outgoing flows are the condition that selects that path.

### Pool and Lane Structure

Pools contain lanes. Lanes contain elements and flows. The pool keyword wraps everything.

```
pool [pool-id] "[Pool Label]" {

  lane [lane-id] "[Lane Label]" {
    [elements declared here]
  }

  lane [lane-id-2] "[Lane Label 2]" {
    [elements declared here]
  }

  [flows declared here — both within and crossing lanes]
}
```

Flow declarations inside the pool block but outside any lane block are legal. This is the preferred location for cross-lane flows since they are not owned by a single lane.

Flows can be declared inside a lane block (if both source and target are in that lane) or in the pool block body (for cross-lane flows). Both patterns are valid.

### Message Flow (Between Pools)

For diagrams with multiple pools:

```
pool [pool-a] "[Pool A]" { ... }
pool [pool-b] "[Pool B]" { ... }

message [source-id] --> [target-id]: "[message label]"
```

Message flow is experimental in the current prototype renderer. Use it for DSL specification purposes but verify SVG output in the playground.

## Generation Workflow

Execute in order. Do not skip steps.

### Step 1 — Extract Process Information

From the user's input (natural language description, existing flowchart, table, bullet list, or prose):

- Identify the actors or systems involved (these become lanes or pools)
- Identify the trigger (start event — what initiates the process)
- Identify the end state(s) (end events — what conditions terminate the process)
- List all work steps (tasks — what each actor does)
- Identify all decision points (gateways — where the path branches)
- Identify all decision outcomes (gateway outgoing flows and their conditions)
- Identify any automated or system steps (service tasks)
- Identify any human approval or review steps (user tasks)
- Identify message exchanges between separate organizational units (message flows)

If any of these are ambiguous, state your assumptions explicitly before producing the diagram — do not ask clarifying questions that would stall output. Make a reasonable interpretation and label it.

### Step 2 — Determine Structural Model

Decide:

- **Single pool, multiple lanes:** One organization, multiple roles or departments. Use when all actors are inside one company or system boundary.
- **Multiple pools:** Two or more organizations. Use when message flows cross organizational boundaries (customer to vendor, company to partner, system to external service).
- **No pool/lane wrapper:** Use only for simple linear processes with one actor or when the user explicitly wants a flat model.

For business process documentation in professional contexts, default to single pool with multiple lanes unless the process is explicitly cross-organizational.

### Step 3 — Assign IDs

Assign short, lowercase, hyphen-free IDs to all elements before writing the DSL. Convention:

- Start events: `s1`, `s2`
- End events: `e1`, `e2`
- Tasks: `t1`, `t2`, `t3` (or semantic IDs like `review`, `approve`)
- Gateways: `g1`, `g2` (or semantic IDs like `approved`, `threshold-met`)
- Intermediate events: `ev1`, `ev2`

IDs must be unique within the diagram. Keep them short — they appear in flow declarations repeatedly.

### Step 4 — Write the DSL

Apply all rules from the DSL Reference section above. Additional constraints:

- Every diagram must have at least one `start` event and at least one `end` event.
- Every `xor` gateway must have at least two outgoing flows, each with a condition label.
- Every `and` gateway (split) must have a corresponding `and` gateway (join) that re-merges the parallel paths, unless the parallel paths terminate in separate end events.
- No orphan elements — every element must appear in at least one flow declaration.
- No circular flows in the first pass. If the process has loops (retry, rework, repeat), model them with a second gateway that branches back to the rework start point.
- Declare all flows at the pool level (outside individual lane blocks) for cross-lane flows. Only declare flows inside a lane block if both source and target are definitively within that lane.

### Step 5 — Self-Validate

Before outputting, check:

- [ ] `bpmn-beta` on line 1
- [ ] All IDs referenced in flows are declared as elements
- [ ] All `xor` gateways have at least two outgoing labeled flows
- [ ] No element is an island (appears in no flow)
- [ ] Pool and lane brackets are properly nested and closed
- [ ] All string labels are in double quotes
- [ ] No reserved keywords used as IDs (`pool`, `lane`, `start`, `end`, `task`, `xor`, `and`, `or`, `message`)

If any check fails, correct before outputting.

### Step 6 — Output

Produce the complete bpmn-beta diagram inside a fenced code block:

```mermaid
bpmn-beta
accTitle: [descriptive title]

pool [id] "[label]" {

  lane [id] "[label]" {
    [elements]
  }

  [cross-lane flows]
}
```

Follow the code block immediately with a compact element inventory:

**Elements:** [n] tasks, [n] events, [n] gateways, [n] lanes, [n] pools  
**Flows:** [n] sequence flows[, n message flows if applicable]

## Validation Workflow

When the user provides existing bpmn-beta code for validation:

1. Check every element declaration for correct keyword spelling
2. Check every flow for existence of both source and target IDs
3. Check gateway cardinality (xor: ≥2 outgoing; and: matching split/join unless deliberate)
4. Check bracket nesting (pool > lane, all closed)
5. Check that all labels are double-quoted
6. Report issues as a numbered list: `[Line N] [Issue description] — [Correction]`
7. Produce a corrected version if issues were found

---

## Explanation Workflow

When the user asks what a bpmn-beta element does, how to use a specific construct, or how the DSL maps to BPMN 2.0:

1. State the element name and its BPMN 2.0 equivalent
2. Show the syntax in a code block
3. Give a one-sentence usage rule
4. Show a minimal working example (3–5 elements, 2–3 flows) in a fenced code block

Do not reproduce the full DSL reference in an explanation response. Answer the specific question.

## Scope Boundaries

Always be honest about these constraints:

**In scope:**
- BPMN 2.0 Descriptive Conformance subset: start/end events, user/service/script tasks, XOR/AND/OR gateways, sequence flows, pools, lanes
- Message intermediate events, timer intermediate events, error end events
- Message flows between pools

**Not in scope (do not generate):**
- Boundary events on tasks
- Transaction subprocesses
- Compensation events
- Data objects and data stores
- Choreography diagrams
- Conversation diagrams
- BPMN XML import or export
- Process engine semantics (bpmn-beta is descriptive, not executable)

If the user requests an out-of-scope element, state clearly that it is outside the current DSL scope and offer the closest available approximation with a note explaining the difference.

## Mermaid Theme Integration

bpmn-beta diagrams honor Mermaid themeVariables. If the user also has a theme palette (from the `mermaid-theme` skill or otherwise), prepend the `%%{init}%%` block before the `bpmn-beta` keyword:

```mermaid
%%{init: { 'theme': 'base', 'themeVariables': { ... } }}%%
bpmn-beta
accTitle: [title]
...
```

If no theme is specified, output the diagram without any init block. Do not default to a specific palette.

---

## Output Rules

- Always produce the complete, syntactically valid bpmn-beta diagram — never a partial sketch.
- Never produce bpmn-beta syntax from memory of BPMN XML or other tools. Use only the keywords and patterns defined in this skill.
- If you are uncertain about a process step's correct classification (task type or gateway type), use `task` or `xor` as the conservative default and note your assumption.
- Do not produce flowchart syntax as a substitute for bpmn-beta. They are different diagram types with different semantics.
- The output is the product. Keep explanation text minimal unless the user asks for explanation.

### 6.4 Supporting File: `references/dsl-spec.md`

The complete formal DSL specification for bpmn-beta, written as a developer-facing reference document. This is distinct from the SKILL.md body (which is instruction-oriented) — the spec is the authoritative grammar source.

Content includes: BNF-style grammar notation for each element type, full keyword table, ID naming rules, flow declaration rules, nesting rules, and reserved word list.

**Replit instruction:** Extract and formalize from the DSL Reference section of the overkillhill.com/projects/bpmn-for-mermaid/ project page and from the GitHub repo's existing DSL documentation. Expand into BNF notation for the pool/lane/element/flow grammar.

### 6.5 Supporting File: `references/bpmn-element-map.md`

Two-way mapping table: BPMN 2.0 standard element name → bpmn-beta keyword (and vice versa). Covers all elements in the Descriptive Conformance subset plus a third column listing elements that are out of scope for v1 with a brief "closest approximation" note.

### 6.6 Supporting File: `references/known-limitations.md`

The honest scope document. What bpmn-beta is. What it isn't. Current prototype parser limitations. Elements that are specified but not yet fully rendered (pools/lanes experimental status). Three annotated example files, each containing: the business context (one paragraph), the natural-language process description used as input, the generated bpmn-beta output, and inline callouts explaining why each element was chosen.
