# BPMN for Mermaid — Technical/IP Disclosure and Market Validation Write-Up

**Working title:** BPMN for Mermaid
**Repository:** `OKHP3/mermaid-diagram-bpmn`
**DSL keyword:** `bpmn-beta`
**Asset class:** AI-assisted developer tooling prototype, diagramming DSL, process-modeling renderer, open-source contribution candidate
**Current status:** Working prototype, not yet a production Mermaid plugin, not yet an upstream Mermaid diagram type

This write-up is framed like a **technical disclosure package** for IP evaluation, acquisition diligence, contributor positioning, or eventual patent counsel review. It is not legal advice, and it should not be treated as a substitute for a patent attorney’s novelty search, claim drafting, or freedom-to-operate review.

---

## 1. Executive Summary

**BPMN for Mermaid** is a working prototype for a text-first diagramming system that enables users to author Business Process Model and Notation diagrams using a Mermaid-like DSL, then render those diagrams as BPMN-style SVG output in a browser-based playground. The project addresses a clear gap: Mermaid supports many diagram types, including recent additions such as Venn, Ishikawa, Wardley, architecture, kanban, radar, treemap, and event modeling diagrams, but BPMN is not represented in the current Mermaid syntax navigation. Mermaid’s current syntax reference lists diagram types from flowcharts through TreeView, including Venn, Ishikawa, and Wardley, with no BPMN entry present. ([Mermaid][1])

The core invention is not merely “draw BPMN shapes.” BPMN itself is a public standard, and Mermaid already exists as a text-to-diagram framework. The defensible value is in the **system combination**:

1. A readable, Mermaid-native BPMN DSL called `bpmn-beta`.
2. A parser that converts that DSL into a structured BPMN data model.
3. A diagram database abstraction representing nodes, flows, pools, lanes, accessibility metadata, and future BPMN extensions.
4. A layout engine that positions process objects, including experimental pool/lane support.
5. A direct SVG renderer that draws BPMN-correct visual shapes without a `bpmn-js` runtime dependency.
6. A live browser playground for immediate authoring, validation, rendering, and iteration.
7. A documentation and contribution framework intended to mature the prototype into an external Mermaid-compatible diagram plugin and possibly later an upstream Mermaid contribution.

The public OverKill Hill project page already frames the value proposition cleanly: “Text-first. Standards-aware. Git-native.” It describes the project as a Mermaid-native `bpmn-beta` diagram type for readable, version-controllable BPMN process diagrams, explicitly avoiding XML, heavyweight tools, and a `bpmn-js` runtime dependency. ([OverKill Hill P³™][2])

The GitHub repository similarly describes the project as a Mermaid-native diagram type for business process modeling using a readable, text-first DSL, with the thesis that BPMN is a material Mermaid gap and that the correct path is not forcing BPMN through Mermaid flowcharts but creating a dedicated `bpmn-beta` plugin implementing a documented descriptive subset. ([GitHub][3])

## 2. Problem Being Solved

Business process diagrams occupy an awkward tooling space.

At one end are heavyweight BPMN platforms such as Visio, Signavio, Camunda Modeler, Bizagi, and bpmn.io-style ecosystems. These tools are visually powerful, but they often produce files or XML structures that do not naturally belong in Markdown-first documentation workflows, pull requests, GitHub READMEs, static documentation sites, or AI-generated architecture artifacts.

At the other end are Mermaid flowcharts. Mermaid flowcharts are excellent for general-purpose boxes-and-arrows diagrams, but they are not semantically BPMN. They do not enforce BPMN distinctions between events, activities, gateways, sequence flows, message flows, pools, lanes, and process boundaries. They can approximate a process diagram visually, but they do not give a process analyst confidence that the notation is BPMN-aware.

BPMN itself is a major standard. The Object Management Group describes BPMN as the de facto standard for business process diagrams, intended for stakeholders who design, manage, and realize business processes while remaining precise enough to translate diagrams into software process components. OMG also emphasizes that BPMN provides an easy-to-use flowchart-like notation independent of any particular implementation environment. ([omg.org][4])

OMG further states that BPMN’s goal is to provide a standard notation comprehensible to business users while still representing complex process semantics for technical users, creating a bridge between business process design and implementation. ([omg.org][5])

That is precisely the gap BPMN for Mermaid targets:

> Business users, architects, analysts, developers, and AI systems need a way to express BPMN-like process diagrams as clean text that can live in documentation repositories, render in browsers, and remain readable without exposing users to BPMN XML.

## 3. Proposed Solution

The solution is a **Mermaid-compatible BPMN descriptive subset system**.

It introduces a text syntax beginning with:

```mermaid
bpmn-beta
```

The author writes compact process declarations:

```mermaid
bpmn-beta
accTitle: Purchase Request Approval

start s1 "Request Raised"
task:user t1 "Review Request"
xor g1 "Approved?"
task:service t2 "Issue PO"
end e1 "Done"

s1 --> t1
t1 --> g1
g1 --> t2: "yes"
g1 --> e1: "no"
t2 --> e1
```

The system then parses the text, identifies BPMN process elements, builds an internal diagram model, computes layout, and renders the result as SVG.

The Notion specification positions the solution as a Mermaid-native `bpmn-beta` diagram type implementing a documented BPMN 2.0 descriptive subset for readable, version-controllable process diagrams, explicitly not an attempt to implement the entire BPMN 2.0 execution model. 

The OverKill Hill public page also distinguishes current state from target state: the prototype supports core BPMN primitives, uses a hand-written line parser, renders SVG directly without `bpmn-js`, treats pool/lane/message-flow support as experimental, and keeps Langium grammar, Mermaid External Diagram API packaging, parser validation, and `getStyles` integration on the roadmap. ([OverKill Hill P³™][2])

## 5. Technical Architecture

### 5.1 Input Layer

The input is plain text beginning with the `bpmn-beta` declaration. This mirrors the Mermaid convention that a diagram begins with a declaration indicating which diagram type the parser should use. Mermaid’s syntax documentation states that diagram definitions begin with a declaration of the diagram type, which notifies the parser what kind of diagram the code is supposed to generate. ([Mermaid][1])

The syntax is designed to be:

* human-readable,
* Markdown-compatible,
* AI-generatable,
* version-controllable,
* compact enough for documentation,
* semantically richer than a generic flowchart.

### 5.2 Parser Layer

The current parser is a hand-written line parser. It recognizes node statements, pool statements, lane statements, sequence flows, conditional flows, default flows, message flows, and accessibility directives.

The parser currently supports patterns for:

* start events,
* end events,
* typed tasks,
* XOR gateways,
* OR gateways,
* AND gateways,
* pools,
* lanes,
* conditional flows,
* sequence flows,
* default flows,
* message flows.

The parser also includes logic enforcing that message flows must be declared at the top level rather than inside a pool or lane block. 

This is significant because it moves the project beyond “visual sketching.” It begins to encode BPMN rules and constraints directly into the authoring language.

### 5.3 Diagram Database Layer

The internal `BpmnDb` abstraction holds the parsed diagram as structured data. It defines BPMN nodes, BPMN flows, BPMN pools, and BPMN lanes. Nodes can represent events, tasks, gateways, subprocesses, calls, and notes; flows can represent sequence, conditional, default, message, and association relationships. 

This internal model is critical because it separates **parsing** from **rendering**. Without that separation, the system would simply be a string-to-SVG hack. With it, the solution becomes extensible:

* A future Langium parser can populate the same data model.
* A future Mermaid External Diagram plugin can expose the same data model.
* A future renderer can consume the same model.
* Future validations can be performed against the same normalized structure.
* Future export formats could theoretically be added after the core stabilizes.

### 5.4 Layout Layer

The layout engine currently provides two modes: a flat process layout and a pool/lane layout. It assigns levels to nodes based on flows, groups nodes by level, computes dimensions, positions pools and lanes, and produces layout objects for nodes, edges, pools, and lanes. 

This is not yet a mature BPMN auto-layout engine. It is an initial deterministic placement system. That is acceptable for a prototype. The IP value is not in claiming solved optimal BPMN layout. The value is in establishing the pipeline and demonstrating a workable, extensible layout path.

### 5.5 Rendering Layer

The renderer converts parsed and laid-out BPMN elements into SVG. It draws start events, end events, tasks, task subtype markers, gateways, gateway symbols, flows, arrowheads, pools, lanes, and labels.

The renderer imports the parser, the layout engine, the BPMN data types, and style generation. It then renders SVG nodes and shapes such as circles, rectangles, polygons, markers, and text labels. 

The final renderer wraps output in an accessible SVG using `role="img"`, a title, and a description, then renders pools, flows, and nodes in order. 

This matters for Mermaid alignment. Mermaid’s own “Adding a New Diagram/Chart” guidance emphasizes that a new diagram requires grammar/parsing, rendering, detection, accessibility, themes, comments, and examples. ([Mermaid][6])

### 5.6 Playground Layer

The Playground is the proof that this can be used by non-developers. It provides a live editor, example selector, parse error detection, status ribbon, two-panel source/preview workspace, pan/zoom controls, and experimental labeling. 

The Playground also includes contextual notes for the active example and flags experimental examples with warnings that layout approximations apply. 

For IP evaluation, this is important because the product is not just a library. It is a **complete authoring and validation environment**.

## 6. Distinction from Existing Tools

### 6.1 Distinction from Mermaid Flowcharts

Mermaid flowcharts are flexible but semantically weak for BPMN. They can draw boxes, diamonds, arrows, and labels, but they do not know whether a symbol is a BPMN task, event, gateway, sequence flow, or message flow. BPMN for Mermaid encodes BPMN concepts directly into the syntax and data model.

**Difference:** Flowchart is generic shape syntax. `bpmn-beta` is domain-specific process notation.

### 6.2 Distinction from BPMN XML Tools

Traditional BPMN tools often center around BPMN XML interchange. That is useful for execution engines and professional BPM suites, but it is hostile to lightweight documentation workflows.

BPMN for Mermaid intentionally rejects XML as the primary authoring layer. It uses clean text syntax and treats XML import/export as out of scope for v1. The public page explicitly says this is not BPMN XML round-tripping and not full BPMN 2.0 conformance. ([OverKill Hill P³™][2])

**Difference:** BPMN XML tools optimize for standard interchange and execution tooling. BPMN for Mermaid optimizes for readable authoring, version control, documentation, and AI generation.

### 6.3 Distinction from `bpmn-js`

`bpmn-js` is a powerful BPMN rendering/modeling ecosystem, but this project deliberately avoids it as a runtime dependency. The public page states the renderer produces BPMN shapes from scratch with no `bpmn-js` dependency, keeping bundle size manageable for Mermaid’s contribution bar. ([OverKill Hill P³™][2])

**Difference:** `bpmn-js` is a mature BPMN modeler/renderer ecosystem. BPMN for Mermaid is a lightweight Mermaid-native syntax and rendering path.

### 6.4 Distinction from PlantUML

PlantUML already supports many diagram families and has BPMN-related capabilities in some contexts. However, PlantUML is not Mermaid, and it does not solve Mermaid’s ecosystem gap. Mermaid’s strength is its Markdown-native adoption across documentation tools and developer workflows. BPMN for Mermaid is aimed specifically at that Mermaid ecosystem.

**Difference:** PlantUML can be a competing text-diagram system; BPMN for Mermaid is an attempt to fill Mermaid’s own native BPMN gap.

### 6.5 Distinction from the Emrich / DFKI Mermaid BPMN Proposal

The Notion project identifies Mermaid issue #7699 as a competing or parallel proposal with an academic pedigree and a more metadata-heavy, XML-flavored syntax. The documented strategy is to engage constructively, present this prototype as a readability-first alternative, and avoid prematurely merging incompatible DSL approaches. 

**Difference:** The apparent competing proposal is closer to a structured metadata representation. BPMN for Mermaid is intentionally more Mermaid-native and prose-like.

## 7. Potential Novelty and Protectable IP

A sober patent/IP review should separate what is **not novel** from what may be **protectable**.

### 7.1 Not likely novel by itself

The following are likely prior art or public domain concepts:

* BPMN notation.
* SVG rendering.
* Text-to-diagram conversion.
* Mermaid-style diagram syntax.
* Browser-based diagram editors.
* BPMN XML.
* Parsing a DSL into an AST-like structure.
* Rendering tasks as rectangles and gateways as diamonds.
* Markdown diagrams.
* AI-generated diagram text.

None of those should be treated as the invention by themselves.

### 7.2 Potentially protectable combination

The stronger IP thesis is the **specific combination and method**:

> A system and method for authoring BPMN descriptive-subset diagrams in a Mermaid-compatible textual DSL, parsing said DSL into a normalized BPMN diagram database, validating BPMN-specific structural constraints, computing a deterministic layout, and rendering accessible, theme-aware SVG output without dependency on a BPMN XML runtime engine.

The strongest protectable angles may include:

1. **Readable BPMN DSL design**

   * Compact syntax representing BPMN semantics without BPMN XML attribute noise.
   * Direct support for events, tasks, gateways, pools, lanes, and flow operators.
   * Syntax optimized for human authors and LLM generation.

2. **Rule-aware textual BPMN authoring**

   * Message flows must be top-level and cross-pool.
   * Sequence flows are constrained within process context.
   * Lanes are scoped within pools.
   * Future grammar can enforce BPMN-valid structure.

3. **Intermediate BPMN diagram database**

   * Parser-independent representation of nodes, flows, pools, lanes, and metadata.
   * Renderer-independent data model supporting future parser and layout backends.

4. **No-XML authoring, optional future XML**

   * User writes lightweight DSL, not BPMN XML.
   * XML import/export is deliberately decoupled from diagram authoring.

5. **Mermaid External Diagram compatibility path**

   * Mermaid’s external diagram interface requires an external definition with an ID, detector, and loader. ([Mermaid][7])
   * The project architecture is already aligned toward an external plugin before any upstream Mermaid inclusion.

6. **AI-generation readiness**

   * Syntax designed to be generated by LLMs reliably.
   * Short IDs, predictable keywords, and low-boilerplate examples reduce generation failure.
   * This is valuable in agentic documentation workflows.

7. **Integrated authoring and validation playground**

   * Live editor.
   * Parse feedback.
   * Visual rendering.
   * Example corpus.
   * Experimental labeling.
   * Roadmap and DSL documentation.

### 7.3 Candidate invention title

> **System and Method for Text-Based Authoring and Rendering of BPMN Process Diagrams Using a Mermaid-Compatible Domain-Specific Language**

### 7.4 Candidate abstract

A computer-implemented system receives a textual business process diagram definition written in a Mermaid-compatible domain-specific language. The system identifies a BPMN diagram declaration, parses process elements including events, tasks, gateways, flows, pools, and lanes, and stores the result in an intermediate BPMN diagram database. A layout engine computes positions for nodes, flows, pools, and lanes according to BPMN-aware containment and connection rules. A rendering engine generates an accessible, theme-aware SVG representation of the process diagram without requiring BPMN XML import/export or a BPMN-specific runtime renderer. The system enables process diagrams to be authored, reviewed, version-controlled, and generated by humans or AI systems in Markdown-compatible environments.

## 8. Draft Claim Concepts for Counsel Review

These are not legal claims. They are technical claim concepts that could be handed to counsel.

### Independent method claim concept

A computer-implemented method comprising:

1. receiving a text input comprising a diagram type declaration corresponding to a BPMN-oriented diagram language;
2. parsing the text input to identify BPMN process elements including at least events, tasks, gateways, and directed flows;
3. storing the identified BPMN process elements in an intermediate diagram database comprising node objects and flow objects;
4. computing a diagram layout from the intermediate diagram database;
5. rendering an SVG diagram comprising BPMN visual notation corresponding to the node objects and flow objects;
6. presenting the SVG diagram in a browser-based preview interface.

### Dependent claim concepts

* The method further comprises parsing pool and lane block contexts and associating node objects with pool and lane identifiers.
* The method further comprises rejecting or flagging message flow declarations within pool or lane block contexts.
* The method further comprises distinguishing sequence flows, conditional flows, default flows, and message flows based on textual flow operators.
* The method further comprises generating accessibility metadata from textual `accTitle` and `accDescr` directives.
* The method further comprises rendering gateway nodes with BPMN-specific markers including XOR, OR, and AND markers.
* The method further comprises rendering task subtype markers including user task, service task, script task, send task, and receive task markers.
* The method further comprises exposing the diagram language as an external diagram definition compatible with a host diagramming library.
* The method further comprises using a language grammar to generate a parser for the BPMN-oriented textual diagram language.
* The method further comprises providing a live playground that simultaneously displays editable source text and rendered diagram output.
* The method further comprises labeling incomplete or experimental diagram features in the user interface.

### System claim concept

A system comprising:

* a textual source editor;
* a parser configured to convert a BPMN-oriented textual diagram definition into structured process objects;
* a diagram database storing process objects;
* a layout engine configured to place process objects;
* an SVG renderer configured to render BPMN visual shapes;
* a preview interface configured to display rendered diagrams and parse errors.

### Computer-readable medium claim concept

A non-transitory computer-readable medium storing instructions that, when executed, cause one or more processors to parse a Mermaid-compatible BPMN textual diagram definition, generate a BPMN data model, compute diagram layout, and render BPMN-style SVG output in a browser environment.

## 9. Marketplace Validation

### 9.1 Standards-driven demand

BPMN is not a niche notation. OMG describes it as the de facto standard for business process diagrams and emphasizes its dual role: understandable to business stakeholders and precise enough for software process translation. ([omg.org][4])

That creates a persistent market need for tools that can express BPMN across:

* enterprise architecture,
* process improvement,
* workflow automation,
* business analysis,
* software delivery,
* compliance documentation,
* transformation programs,
* AI-generated process documentation.

### 9.2 Mermaid ecosystem demand

Mermaid has become a major text-to-diagram standard in developer documentation workflows. The current Mermaid syntax documentation presents Mermaid as a system where syntax, deployment, and configuration constitute the whole of Mermaid, and where diagrams begin with a diagram type declaration. ([Mermaid][1])

The important market signal is not just Mermaid’s existence. It is Mermaid’s **diagram-type extensibility**. Mermaid’s own documentation describes adding new diagrams through grammar/parsing, rendering, detection, accessibility, theming, and examples. ([Mermaid][6])

That means BPMN for Mermaid is aligned with the framework’s documented expansion model, not bolted on as an unrelated hack.

### 9.3 Platform fit

The target market is not “people who want another BPMN modeler.” That market is crowded.

The more precise market is:

> People who want BPMN-like process diagrams to live in Markdown, GitHub, documentation portals, architecture repositories, AI workbenches, and CI/CD-friendly technical documentation.

The public project page already articulates this positioning: write BPMN as a Markdown code fence, commit it alongside code, let LLMs generate it, have process analysts read it, and render BPMN-correct shapes without XML, graphical editors, or `bpmn-js`. ([OverKill Hill P³™][2])

### 9.4 AI-era validation

The AI tailwind is real. Recent research is already exploring business process management in the age of generative AI, including “Large Process Models” that combine LLM correlation capabilities with analytical precision and knowledge-based reasoning. ([arXiv][8])

There is also emerging research on LLM performance for business process management tasks, including the need to benchmark LLMs against domain-specific BPM tasks rather than only general-purpose language tasks. ([arXiv][9])

Separately, research is appearing around converting visual flowcharts into editable Mermaid code, motivated by the problem that static process diagrams are hard to edit, reuse, and keep synchronized with rendered output. ([arXiv][10])

BPMN for Mermaid sits at the intersection of those trends:

* process modeling,
* LLM-generated structured diagrams,
* Mermaid code,
* version-controllable documentation,
* editable process artifacts.

### 9.5 Adjacent market evidence

Business process work is economically large. A 2025 Times of India report citing Everest Group describes the global third-party BPM industry as valued over $300 billion, while noting growing demand for AI and process automation. This is not the same as the direct software market for a Mermaid BPMN plugin, but it validates that business process documentation, process automation, and process transformation are major enterprise concerns. ([The Times of India][11])

### 9.6 Market wedge

The wedge is narrow but valuable:

| Segment                 | Pain                                           | Why BPMN for Mermaid fits                              |
| ----------------------- | ---------------------------------------------- | ------------------------------------------------------ |
| Enterprise architects   | Need process diagrams beside architecture docs | Git-native text diagrams fit architecture repositories |
| Process analysts        | Need BPMN semantics without heavy tooling      | Readable DSL reduces tool friction                     |
| Developers              | Need process context in READMEs and ADRs       | Markdown-compatible syntax fits dev workflows          |
| AI tool builders        | Need reliable structured output                | DSL is short, regular, and LLM-friendly                |
| Documentation teams     | Need diagrams that can be reviewed and updated | Text diffs and pull requests replace screenshots       |
| Open-source maintainers | Need lightweight examples and docs             | No proprietary BPMN tooling required                   |

## 13. Current Limitations

The current project is promising but not finished.

Known limitations include:

1. **Not an official Mermaid diagram type**

   * It does not yet render natively inside Mermaid consumers.

2. **Not yet packaged as an external Mermaid plugin**

   * The target external plugin architecture is documented, but the current artifact is still a React prototype.

3. **Parser is hand-written**

   * Good for iteration; insufficient for upstream-quality grammar maturity. Notion records the strategy as hand-written prototype first, Langium for plugin v1. 

4. **Pool/lane/message flow support is experimental**

   * The public page tells users to verify output before relying on it. ([OverKill Hill P³™][2])

5. **No BPMN XML**

   * This is intentional for v1, but buyers may ask for it.

6. **No execution semantics**

   * Also intentional. The target is descriptive diagramming, not workflow execution.

7. **No formal conformance certification**

   * The project should avoid claiming full BPMN 2.0 conformance.

8. **No mature layout engine**

   * Layout is usable for prototype validation but will need improvement for production adoption.

9. **Limited adoption metrics**

   * Repository currently has no stars or forks visible in the GitHub page snapshot, meaning market validation is conceptual and strategic, not traction-based yet. ([GitHub][3])

## 17. Patentability Risk Assessment

Bluntly: a broad patent on “text-to-BPMN diagrams” is probably weak. There is too much prior art: BPMN, Mermaid, PlantUML, DSLs, SVG rendering, browser editors, BPMN XML tools, and diagram generation systems.

A narrower patent claim may have a better chance if it focuses on:

* Mermaid-compatible BPMN DSL structure,
* BPMN-specific validation rules in text form,
* intermediate diagram database abstraction,
* browser-rendered accessible SVG output,
* no-XML authoring layer,
* AI-generation-optimized syntax patterns,
* external plugin integration with a host diagram framework.

The invention is strongest as a **specific system and method**, not as a broad conceptual monopoly.

From a practical business perspective, the better strategy may be:

| Protection mode              | Practical value                                            |
| ---------------------------- | ---------------------------------------------------------- |
| Copyright in source code     | Stronger than broad software patent in many contexts       |
| Trademark / project identity | Useful if the tool gains adoption                          |
| Documentation / know-how     | Valuable for sale or consulting                            |
| Open-source reputation       | Likely highest near-term value                             |
| Patent application           | Worth counsel review, but not the first lever I would pull |
| Trade secret                 | Limited, because the repo and docs are already public      |

| Buyer type                          | What they value                                            |

A polished open-source prototype with docs and no adoption metrics.

### Mid-range value

A working external plugin with stable syntax, examples, tests, and public Mermaid community engagement.

Right now, the asset is between low and mid. It becomes materially more valuable once the plugin packaging and community validation happen.
