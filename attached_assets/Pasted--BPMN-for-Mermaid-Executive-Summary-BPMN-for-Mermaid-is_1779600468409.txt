# BPMN for Mermaid

## Executive Summary

**BPMN for Mermaid** is best understood as a **Mermaid-native, text-first BPMN proposal** rather than a conventional BPM suite, workflow engine, or visual modeler. Its core bet is simple: the market already has strong BPMN editors, but they are largely XML-first, GUI-first, or runtime-first. This project instead targets the gap between **documentation-grade diagrams**, **Git-native version control**, and **LLM-friendly authoring** by introducing a readable `bpmn-beta` DSL that can live inside a Markdown code fence and eventually ship as a Mermaid external diagram plugin. The public project page is explicit that the current release is a **prototype**, with a hand-written parser, heuristic layout, direct SVG rendering, and experimental pools/lanes support. The long-term path is also explicit: move to **Langium**, package to the **Mermaid External Diagram API**, add `getStyles`, testing, accessibility parity, and only then pursue an upstream Mermaid contribution. citeturn44view0turn20view1turn9view2

The strongest validation for the concept is not current adoption volume. It is **ecosystem fit**. Mermaid’s official docs continue to position new diagram types around grammar/parsing, rendering, detector keys, accessibility metadata, and theming hooks; Mermaid also lists native/community integrations across GitHub, GitLab, Notion, Azure DevOps, Loop, Obsidian, and many other environments. That means a successful BPMN-for-Mermaid plugin would plug into an already massive text-diagram distribution surface rather than needing to create a new viewing platform from scratch. In parallel, Mermaid issue **#7699** proves the demand signal is real: BPMN support is already an active, open “new diagram” request, with use cases spanning academic publishing, business documentation, model-driven engineering, LLM-assisted modeling, and version-controlled documentation. citeturn20view0turn20view1turn9view2turn41view0turn19view2

The project is strategically differentiated from classic BPMN tooling in three ways. First, it deliberately **does not chase executable BPMN** or BPMN XML round-tripping in v1. Second, it treats readability for humans and LLMs as a first-class product requirement. Third, it tries to meet Mermaid’s contribution bar by avoiding a heavyweight `bpmn-js` runtime dependency. That means the near-term product is best framed as **“BPMN for docs, docs-as-code, AI-assisted drafting, and lightweight review”**, not “BPMN for process execution.” That scope discipline is a strength, not a weakness. citeturn44view0turn33view0

The highest-confidence recommendation is therefore this: **package the project as the best-in-class Markdown-native BPMN authoring layer**, not as a replacement for Camunda, Visio, or enterprise BPM suites. The repo should be tightened immediately around status signaling, DSL documentation, contribution guidance, and security hygiene. The public narrative should consistently say: **prototype now, external Mermaid plugin next, upstream proposal later**. The ready-to-commit files later in this report are written to support exactly that positioning. citeturn44view0turn13view3

## Current Implementation and Architecture

The repo root already establishes the project identity clearly. It describes BPMN for Mermaid as **“a Mermaid-native diagram type for business process modeling using a readable, text-first DSL”**, explicitly frames `bpmn-beta` as a dedicated plugin path rather than a flowchart hack, labels the DSL unstable, links to the live demo, and provides a minimal development command using `pnpm --filter @workspace/mermaid-diagram-bpmn run dev`. The repository currently shows **23 commits**, an MIT license, and a TypeScript-heavy codebase with CSS, HTML, JavaScript, and Mermaid assets also present. citeturn13view3

The public project page supplies the best current implementation snapshot. It says the prototype already supports **core BPMN primitives** in the playground, uses a **hand-written line parser** rather than Langium, renders **SVG directly with no `bpmn-js` dependency**, and treats **pool/lane/message-flow support as experimental**. It also says the prototype includes **four canonical example diagrams**, a **six-page React app** consisting of **Home, Playground, DSL Reference, Architecture, Roadmap, and About**, and a current progression from “prototype shipped” to a “v0.1 — Pools, Lanes & Plugin API” phase. citeturn44view0

## Ecosystem, Contribution Path, and Competitive Landscape

Mermaid’s official contribution guidance maps almost perfectly onto what BPMN for Mermaid says it still needs. Mermaid’s docs say a new diagram path requires **grammar/parsing**, **rendering**, and **diagram type detection**, and specifically call out **Langium** as the grammar route used in exemplar PRs. Mermaid’s external plugin API surface is intentionally small — `id`, `detector`, and `loader` — but the broader contribution norms also require parity on directives, comments, accessibility, and theming. Mermaid’s theming docs, meanwhile, make it clear that diagram-level theme integration flows through `getStyles` and `themeVariables`, and that only the `base` theme is modifiable in the standard way. citeturn20view0turn20view1turn20view2turn9view2turn34view2

That means the project’s own roadmap is well aimed. The public page’s sequence — hand-written parser first, then pools/lanes/plugin API work, then Langium, npm packaging, accessibility, theming, tests, and finally a Mermaid core proposal — is not just sensible. It is **aligned with Mermaid’s official mechanics**. In plain English: the product direction is not wandering. It is already pointed at the right gate. citeturn44view0turn20view0turn9view2

The community landscape is also clear. Mermaid issue **#7699** is already open under labels for **enhancement** and **new diagram**, with an alternative BPMN proposal from Andreas Emrich that uses a far more attribute-heavy DSL. That issue body explicitly argues that Mermaid lacks BPMN today, and names use cases that strongly overlap this project’s stated value proposition. The real competitive question inside the Mermaid ecosystem is therefore **not** “is BPMN needed?” It is “which BPMN syntax best fits Mermaid’s culture and contribution bar?” On that question, BPMN for Mermaid has a sharp strategic position: it is betting that Mermaid will prefer **readability and Markdown affinity** over a more XML-shaped notation. citeturn19view2turn19view3turn44view0

The larger distribution opportunity is significant. Mermaid’s official integration page lists **GitHub, GitLab, Notion, Azure DevOps, Loop, Obsidian, GitBook, Joplin, and many others** as community or native integration surfaces. BPMN as a Mermaid-compatible diagram type therefore has a distribution logic that classic BPMN tools do not: it can ride the same text-diagram channels where engineers and analysts already write, comment, review, and publish documentation. That is the core commercialization angle. Not “replace BPM suites,” but “put BPMN wherever Mermaid already lives.” citeturn41view0

## Literature, Prior Art, and Market Validation

The standards backdrop is solid. OMG describes BPMN 2.0.2 as the de-facto standard for business process diagrams, intended to be understandable to stakeholders while also precise enough for translation into software process components; OMG also publishes the normative PDF plus machine-readable XML schemas and related artifacts. That matters because BPMN for Mermaid is not inventing a new process notation from scratch. It is trying to create a **new authoring surface for an existing standard family**. citeturn33view0

Recent literature strengthens the case for text-first and AI-assisted process modeling. The open Mermaid issue itself references a forthcoming DFKI paper about Mermaid diagrams for BPMN, which is already a public disclosure that text-based BPMN-in-Mermaid is being explored academically. Outside that issue, recent arXiv work shows strong activity around **LLM-based BPMN generation**, including a JSON-mediated BPMN assistant, multi-stage natural-language-to-BPMN XML reconstruction, and conversational systems that interview users and generate BPMN process models. There is also adjacent Mermaid-specific scholarship on converting flowcharts into editable Mermaid code and benchmarking Mermaid diagram generation quality. Put bluntly: the broader market has already moved from “can AI help create process diagrams?” to “which intermediate representation works best for editability, correctness, and human review?” citeturn19view2turn24academia7turn26academia3turn27academia2turn35academia0turn35academia2

The formal-methods literature also helps frame what **not** to do in v1. Research on BPMN correctness, soundness, and execution semantics repeatedly shows that executable BPMN is complicated, ambiguous in places, and difficult to verify. That supports the current project decision to stay in a **descriptive subset** rather than overreaching into a pseudo-engine. A readable authoring DSL for documentation and review is a tractable first product; a faithful execution-semantic system is a very different research and engineering problem. citeturn43academia2turn43academia9turn26academia1

From an IP and prior-art perspective, the field is already crowded at the concept level. Public disclosures plainly exist for **text-to-diagram authoring** in Mermaid and PlantUML, **BPMN XML interchange**, **natural-language-to-BPMN systems**, **domain-specific workflow-to-BPMN transformations**, and now an open **Mermaid BPMN proposal** in issue #7699. That does not mean no protectable IP remains. It does mean any patent theory would need to focus on a **narrow, implementation-specific inventive step** — for example, a particular readable BPMN DSL design, a specific parser/layout/rendering pipeline, or a specific AI-assisted constraint architecture — rather than the broad idea of “describe a process as text and render a BPMN-like diagram.” This is a high-level prior-art observation, not legal advice. citeturn38search4turn38search3turn33view0turn24academia7turn26academia3turn43academia6turn19view2

Market validation is therefore strongest in five adjacent segments. First are **docs-as-code engineering teams** that already use Mermaid in GitHub/GitLab/Notion/Obsidian. Second are **enterprise architects and business analysts** who want BPMN readability without standing up a full BPM suite for every diagram. Third are **AI-assisted modeling experiences** that need a short, predictable textual representation more LLM-friendly than verbose XML. Fourth are **education and training** use cases, where teaching BPMN through text and render loops has lower friction than teaching heavy visual tools first. Fifth are **SaaS platforms already embedding Mermaid** and looking for more diagram types without adopting an entire BPMN engine stack. Those segments are an inference from the standards position of BPMN, Mermaid’s integration footprint, and the use cases named on issue #7699. citeturn33view0turn41view0turn19view2

## Risks and Mitigations

The current risks are manageable, but only if the repo and public language stay brutally honest. The biggest technical risk is **parser debt**: the hand-written parser got you to proof-of-concept quickly, but Mermaid’s own docs are steering new diagrams toward Langium. The second major risk is **scope creep** into full BPMN and XML round-trip expectations. The third is **community collision**, because #7699 already contains another proposal. The fourth is **adoption ambiguity**: if the README and website do not sharply explain that this is docs-grade BPMN for Mermaid rather than execution BPMN, users will import the wrong expectations, then punish the project for not being Camunda. citeturn20view0turn44view0turn19view2

### Suggested `README.md`

```md
# BPMN for Mermaid

A Mermaid-native `bpmn-beta` diagram type proposal for readable, version-controllable BPMN process diagrams.

Write business processes as text.
Render BPMN-correct shapes.
Keep process diagrams next to the code and documentation they describe.

## What this project is

BPMN for Mermaid explores a text-first, Mermaid-native way to author BPMN-style process diagrams using a dedicated diagram keyword:

```mermaid
bpmn-beta
accTitle: Purchase Order Approval

pool company "Company" {
  lane requester "Requester" {
    start     s1  "Need Identified"
    task:user t1  "Submit Purchase Request"
  }

  lane manager "Manager" {
    task:user t2  "Review Request"
    xor       g1  "Approved?"
    end       e2  "Rejected"
  }

  lane procurement "Procurement" {
    task:service t3  "Create Purchase Order"
    end          e1  "PO Issued"
  }

  s1 --> t1
  t1 --> t2
  t2 --> g1
  g1 --> t3: "yes"
  g1 --> e2: "no"
  t3 --> e1
}
```

## Project thesis

Mermaid has a meaningful diagram-type gap: BPMN 2.0 is not represented as a native syntax.

The goal is **not** to force BPMN through `flowchart`.
The goal is to create a dedicated `bpmn-beta` diagram type that:

- feels like Mermaid
- stays readable in plain text
- is friendly to version control and code review
- is simple enough for LLM-assisted generation
- can eventually ship as a Mermaid External Diagram plugin

## Current status

**Status:** Prototype  
**Phase:** v0.1 — Pools, Lanes & Plugin API  
**License:** MIT

### Working now

- Core BPMN primitives in the prototype playground:
  - start/end events
  - tasks
  - gateways
  - sequence flows
- Hand-written line parser
- Heuristic layout
- Direct SVG renderer
- No `bpmn-js` runtime dependency

### Experimental now

- Pools
- Lanes
- Message flows

### Not implemented yet

- Langium grammar
- Mermaid External Diagram API packaging
- Mermaid `getStyles` integration
- Full test parity corpus
- BPMN XML import/export
- Executable BPMN semantics

## Scope boundaries

This project targets a **descriptive subset** of BPMN.

It is intentionally **not**:

- a process engine
- a BPMN XML round-trip tool
- the full BPMN 2.0 specification
- a replacement for Camunda, Visio, or enterprise BPM suites

The aim is documentation-grade BPMN for Markdown, docs-as-code, and AI-assisted process authoring.

## Why this exists

Today, teams usually have to choose between:

1. heavyweight BPMN tools that are GUI-first and often XML-first, or
2. Mermaid flowcharts that are lightweight but not BPMN-correct

`bpmn-beta` is an attempt to bridge that gap.

# bpmn-beta DSL Reference

## Purpose

`bpmn-beta` is a readable, Mermaid-native BPMN DSL proposal focused on the descriptive subset of BPMN.

- Markdown code fences
- Git-friendly process documentation
- human readability

bpmn-beta

accTitle: Purchase Order Approval

## Core element keywords

### Events

| Keyword | Meaning |
|---|---|
| `start` | Start event |
| `end` | End event |
| `event:message` | Intermediate message event |
| `event:timer` | Intermediate timer event |
| `event:error` | Error end event |

### Tasks

| Keyword | Meaning |
|---|---|
| `task` | Abstract task |
| `task:user` | User task |
| `task:service` | Service task |
| `task:script` | Script task |

### Gateways

| Keyword | Meaning |
|---|---|
| `xor` | Exclusive gateway |
| `and` | Parallel gateway |
| `or` | Inclusive gateway |

## Flow operators

| Operator | Meaning |
|---|---|
| `-->` | Sequence flow |
| `--> : "label"` | Labeled / conditional sequence flow |
| `==>` | Default sequence flow |
| `~~>` | Message flow |
| `---` | Association |

## IDs

IDs should follow:

```text
[A-Za-z_][A-Za-z0-9_]*
```

Examples:

- `s1`
- `t1`
- `g1`
- `request_approved`

## Labels

Most nodes accept a quoted label:

```text
task:user t1 "Review Request"
xor g1 "Approved?"
```

## Pools and lanes

### Pool example

```text
pool company "Company" {
  lane requester "Requester" {
    start s1 "Need Identified"
    task:user t1 "Submit Purchase Request"
  }

  lane manager "Manager" {
    task:user t2 "Review Request"
    xor g1 "Approved?"
    end e2 "Rejected"
  }

  lane procurement "Procurement" {
    task:service t3 "Create Purchase Order"
    end e1 "PO Issued"
  }

  s1 --> t1
  t1 --> t2
  t2 --> g1
  g1 --> t3: "yes"
  g1 --> e2: "no"
  t3 --> e1
}
```

## Rules

- Sequence flows must stay inside a pool
- Message flows cross pools and should be declared at top level
- Lanes are only one level deep in current scope
- Nested lanes beyond one level are deferred
- Comments use Mermaid-style `%%`

## Comments

```text
%% This is a comment
```

## Canonical minimal example

```text
bpmn-beta
accTitle: Purchase Request Approval

start s1 "Request Raised"
task:user t1 "Review Request"

task:service t2 "Issue PO"
end e1 "Done"

s1 --> t1
t1 --> g1
g1 --> t2: "yes"
g1 --> e1: "no"
t2 --> e1
```

## Out of scope for v1

The following are intentionally deferred:

- boundary events
- transactions
- choreography diagrams
- conversation diagrams
- BPMN XML import/export
- executable semantics
- compensation
- multi-instance markers
- deeply nested lane structures
- data objects / stores / groups

## Design principle

When in doubt, prefer:

- Mermaid-native readability
- shorter syntax
- lower ambiguity
- explicit scope boundaries
- structures that are easy for humans and LLMs to get right

## Supported status

This repository is currently a prototype and research-stage implementation.

Security fixes will be handled on a best-effort basis while the project remains pre-1.0.

## Reporting a vulnerability

Please do **not** open a public issue for a suspected security problem.

Instead, report it privately to the maintainer using the project contact path listed on the public project page or repository profile.

Include:

- affected file(s) or module(s)
- reproduction steps
- impact assessment
- proof-of-concept if safe to share
- suspected dependency involvement, if any

## What counts as a security issue here

Examples:

- XSS or injection in playground rendering
- unsafe rendering of untrusted labels or metadata
- dependency-level vulnerabilities with real exploit relevance
- build or preview routes exposing data unexpectedly

## What does not count

Examples:

- syntax bugs
- parser failures without security impact
- layout defects
- BPMN semantic disagreements
- cosmetic SVG issues

Before any public package release, the project should add:

- lockfile review
- dependency audit in CI
- release notes for dependency upgrades
- explicit review of any SVG / HTML rendering boundary

1. Private report received
2. Triage and reproduction
3. Fix prepared

### Open questions and limitations

The first open question is simple: **which surface is canonical when sources disagree?** Right now, the OverKill Hill page is the most complete public narrative, but the repo should become the canonical contributor truth. The second is **example-count drift** — the website says four canonical examples, while earlier file-level inspection suggested more example coverage. The third is **public-surface verification drift** — Notion, Replit, and the GitHub Pages playground were not all directly inspectable in this browser session, so the repo should publish a single status page with verified current URLs and expected behaviors. citeturn44view0turn13view3turn18view0turn18view1turn18view2

The last open question is strategic and important: **should the project remain a narrow descriptive subset permanently, or eventually support optional bridges into BPMN XML?** My strong opinion is that v1 should stay narrow. If you get the readable Mermaid-native authoring layer right first, you create an actual product identity. If you chase XML parity first, you risk becoming a worse Camunda and a worse bpmn.io at the same time. citeturn44view0turn33view0
